# Проект: «Научный календарь»

Сайт с анонсами научно-популярных лекций. Данные собираются с elementy.ru/events (`scrape.py`) с merge-логикой (новые/изменённые/удалённые события, пометка `updated`), сайт собирается из `data/events.json` сборщиком `build.py` в папку `site/`. Публикация — GitHub Pages через `.github/workflows/deploy.yml` (каждый `git push` в `master` пересобирает и публикует сайт).

Локальный сервер `serve.py` (команда `python serve.py`, адрес http://localhost:8000) раздаёт папку `site/` и через кнопку «Обновить данные» на главной странице выполняет полный цикл: `scrape.py` → `build.py` → `git add -A; git commit; git push`. Это штатный сценарий публикации пользователем — отдельного разрешения на push он не требует (подтверждение пользователя уже есть в самом интерфейсе кнопки).

Планируемое развитие — пайплайн автоматического сбора из нескольких источников (см. раздел 9 памятки). Событие по умолчанию подходит под стандарты «Элементов»; спорные случаи требуют подтверждения пользователем.

Пользователь — новичок в терминале/git. Объясняй шаги по-русски, без жаргона, проверяй команды перед запуском.

## Обязанность

- **Поддерживать актуальность файла `ПАМЯТКА.md`** (шпаргалка пользователя по проекту): при любом изменении команд, структуры проекта, рецептов работы — обновлять соответствующие разделы и при необходимости коммитить вместе с изменениями.
- Не удалять и не переименовывать `ПАМЯТКА.md` и `AGENTS.md` без явного запроса пользователя.
- Коммитить и пушить только когда пользователь явно об этом просит (но помнить: каждая «публикация» нового состояния проекта = `git add -A; git commit -m ...; git push`).
- **Перед КАЖДЫМ коммитом (обязательное правило)** — проверять валидность всех скиллов детерминированным скриптом `python -X utf8 tools\check_skills.py` (YAML-frontmatter `name`/`description` у всех `.opencode/skills/*/SKILL.md` проверяется штатным YAML-парсером, совпадение `name` с именем каталога, локальные пути из скиллов существуют). Если скрипт нашёл проблемы — исправить их, прогнать заново, и только потом коммитить. Пропускать эту проверку нельзя; её вывод прикладывается к результату.
- **Проверку скиллов нужно прогонять И ПРИ СТАРТЕ: после запуска проекта или открытия новой сессии** (тот же `python -X utf8 tools\check_skills.py`) — чтобы убедиться, что все скиллы загрузились нормально. Зафиксировать параметры всех новых сессий и проектов запрещено, поэтому правила повторяются для каждой команды. Если проверка нашла проблему — исправить и прогнать заново, потом начинать работу.
- **Каждый прототип описания события (формальные поля + текст + HTML) перед показом пользователю ОБЯЗАТЕЛЬНО проходит ОДИН сквозной проход «корректура + пост-проверка»** (объединён с 28.09.2026): самопроверка по скиллу `proofreading` (п. 0: отдельный проход по готовому тексту, список всех nbsp и «ё» с вердиктами) и пост-проверка по скиллу `post-check` (п. 0: ДЕТЕРМИНИРОВАННЫЙ валидатор `tools/check_prototype.py`, затем чек-лист 1–11) выполняются как ОДИН проход по готовому тексту, каждый со своим письменным артефактом. Проход выполняется буквально по чек-листам, пропускать их нельзя; пост-проверка не заменяется «прогоном по памяти» — пункт 0 запускает скрипт, вывод которого прикладывается к результату.
- **Частичная проверка прототипа (правило 01.10.2026)**: правка конкретных полей не требует полной пересборки текста и полной проверки — хватает проверить и пересобрать ТОЛЬКО изменённые поля: `python -X utf8 tools\check_proto_json.py data\prototypes\<ID>\prototype.json --only desc` (области: `fields`/`поля`, `title`, `annot`, `lecturer`, `desc`, `extra`, `authors`; либо номера полей `--only 3,6,13`, `--only 7.4`; работает и с `--fix` — правит только выбранное). Неизвестный элемент списка — понятная ошибка, а не молчаливая проверка не того. Перед показом пользователю прогон всё равно ПОЛНЫЙ (`--only` — для точечных правок в середине работы).
- **Готовые блоки с «Элементов» копируются ДОСЛОВНО (правило 01.10.2026)**: если блок/текст уже готов на «Элементах» (описание автора в базе, подзаголовок лектория и т.п.) — действует простое правило «вырезать код и вставить его в описание». Никаких повторных выяснений оформления, «примерок» типографики и согласований ради nbsp/ё. Такие вставки перечисляются в `prototype.json` верхнего уровня в поле `verbatim_fragments`; валидатор `tools/check_prototype.py` по этому полю пропускает проверки nbsp/ё/тире внутри фрагментов. На собственные тексты прототипа правило не распространяется. Подробности: `event-description` разд. 3г, `proofreading`, ПАМЯТКА.md разд. 4б.
- **Бережное расходование прогонов валидатора (правило 28.09.2026)**: перед показом прототипа валидатор прогоняем МАКСИМУМ два раза — первый прогон сразу после записи прототипа (или после `--fix`), финальный после всех правок. Не гонять валидатор повторно для каждого мелкого исправления: правим все ошибки одним заходом (механику nbsp/«ё»-инвариантов/тире может исправить сам валидатор режимом `--fix`, см. раздел 4б памятки). Старые прототипы (уже загруженные на сайт) валидатором не проверяются и не трогаются.

- **Правило важнее старого образца (правило 30.09.2026)**: опубликованная страница «Элементов» — это образец ВО оформления, но НЕ источник правил: если образец противечит действующему правилу — пишем по правилу (напр. **«Проезд: метро «…»»** — без «до станции метро»; возраст и аннотация — только в фолде 12), и **если правило однозначно — вопрос пользователю не задаём**. Зафиксировано: `event-description` разд. 3в, `proofreading` разд. 1а, `post-check` п. 11, ПАМЯТКА разд. 4б.
