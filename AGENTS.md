# Проект: «Научный календарь»

Сайт с анонсами научно-популярных лекций. Данные собираются с elementy.ru/events (`scrape.py`) с merge-логикой (новые/изменённые/удалённые события, пометка `updated`), сайт собирается из `data/events.json` сборщиком `build.py` в папку `site/`. Публикация — GitHub Pages через `.github/workflows/deploy.yml` (каждый `git push` в `master` пересобирает и публикует сайт).

Локальный сервер `serve.py` (команда `python serve.py`, адрес http://localhost:8000) раздаёт папку `site/` и через кнопку «Обновить данные» на главной странице выполняет полный цикл: `scrape.py` → `build.py` → `git add -A; git commit; git push`. Это штатный сценарий публикации пользователем — отдельного разрешения на push он не требует (подтверждение пользователя уже есть в самом интерфейсе кнопки).

Планируемое развитие — пайплайн автоматического сбора из нескольких источников (см. раздел 9 памятки). Событие по умолчанию подходит под стандарты «Элементов»; спорные случаи требуют подтверждения пользователем.

Пользователь — новичок в терминале/git. Объясняй шаги по-русски, без жаргона, проверяй команды перед запуском.

## Обязанность

- **Поддерживать актуальность файла `ПАМЯТКА.md`** (шпаргалка пользователя по проекту): при любом изменении команд, структуры проекта, рецептов работы — обновлять соответствующие разделы и при необходимости коммитить вместе с изменениями.
- Не удалять и не переименовывать `ПАМЯТКА.md` и `AGENTS.md` без явного запроса пользователя.
- **Коммитить и пушить без отдельного запроса, если текущие изменения корректны и всё работает** (правило пользователя 14.10.2026; отменяет прежнее «коммитить только по явной просьбе»): сначала прогнать проверку скиллов (пункт ниже) — если она зелёная, сразу `git add -A; git commit -m ...; git push`. Отдельного разрешения на push ждать не нужно: каждая «публикация» нового состояния проекта — это такой push, и при следующем обновлении сайта изменения всё равно закоммитятся.
- **Перед КАЖДЫМ коммитом (обязательное правило)** — проверять валидность всех скиллов детерминированным скриптом `python -X utf8 tools\check_skills.py` (YAML-frontmatter `name`/`description` у всех `.opencode/skills/*/SKILL.md` проверяется штатным YAML-парсером, совпадение `name` с именем каталога, локальные пути из скиллов существуют). Если скрипт нашёл проблемы — исправить их, прогнать заново, и только потом коммитить. Пропускать эту проверку нельзя; её вывод прикладывается к результату.
- **Проверку скиллов нужно прогонять И ПРИ СТАРТЕ: после запуска проекта или открытия новой сессии** (тот же `python -X utf8 tools\check_skills.py`) — чтобы убедиться, что все скиллы загрузились нормально. Зафиксировать параметры всех новых сессий и проектов запрещено, поэтому правила повторяются для каждой команды. Если проверка нашла проблему — исправить и прогнать заново, потом начинать работу.
- **Недоступность сайтов-источников (правило пользователя 10.10.2026)**: при ошибке запроса к elementy.ru/Timepad/сайту организатора/поисковику — об ошибке ОБЯЗАТЕЛЬНО сообщать пользователю и записывать её в отдельный лог `.opencode/skills/event-description/reference/availability_log.md` (дата+время, URL, тип ошибки, число попыток и интервалы, итог). Если сайт недоступен — повторять через 1 минуту, если не помогло — ещё через 5 минут, дальше по решению пользователя (это была локально повышенная нагрузка, а не постоянный обрыв). Когда проверка автора/дублей из-за недоступности откладывалась — вернуться к ней после того, как сайт снова ответил, и дописать результат в `notes` прототипа.
- **Каждый прототип описания события (формальные поля + текст + HTML) перед показом пользователю ОБЯЗАТЕЛЬНО проходит ОДИН сквозной проход «корректура + пост-проверка»** (объединён с 28.09.2026): самопроверка по скиллу `proofreading` (п. 0: отдельный проход по готовому тексту, список всех nbsp и «ё» с вердиктами) и пост-проверка по скиллу `post-check` (п. 0: ДЕТЕРМИНИРОВАННЫЙ валидатор `tools/check_prototype.py`, затем чек-лист 1–11) выполняются как ОДИН проход по готовому тексту, каждый со своим письменным артефактом. Проход выполняется буквально по чек-листам, пропускать их нельзя; пост-проверка не заменяется «прогоном по памяти» — пункт 0 запускает скрипт, вывод которого прикладывается к результату.
- **Частичная проверка прототипа (правило 01.10.2026)**: правка конкретных полей не требует полной пересборки текста и полной проверки — хватает проверить и пересобрать ТОЛЬКО изменённые поля: `python -X utf8 tools\check_proto_json.py data\prototypes\<ID>\prototype.json --only desc` (области: `fields`/`поля`, `title`, `annot`, `lecturer`, `desc`, `extra`, `authors`; либо номера полей `--only 3,6,13`, `--only 7.4`; работает и с `--fix` — правит только выбранное). Неизвестный элемент списка — понятная ошибка, а не молчаливая проверка не того. Перед показом пользователю прогон всё равно ПОЛНЫЙ (`--only` — для точечных правок в середине работы).
- **Готовые блоки с «Элементов» копируются ДОСЛОВНО (правило 01.10.2026)**: если блок/текст уже готов на «Элементах» (описание автора в базе, подзаголовок лектория и т.п.) — действует простое правило «вырезать код и вставить его в описание». Никаких повторных выяснений оформления, «примерок» типографики и согласований ради nbsp/ё. Такие вставки перечисляются в `prototype.json` верхнего уровня в поле `verbatim_fragments`; валидатор `tools/check_prototype.py` по этому полю пропускает проверки nbsp/ё/тире внутри фрагментов. На собственные тексты прототипа правило не распространяется. Подробности: `event-description` разд. 3г, `proofreading`, ПАМЯТКА.md разд. 4б.
- **Описание автора ИЗ ИСТОЧНИКА — обязательный абзац в тексте описания (правило пользователя 15.10.2026)**: если источник даёт описание автора (должность/звание), оно входит последним абзацем аннотации в форме «<b><i>Имя Фамилия</i></b>&nbsp;— <i>описание из источника</i>.» — без вводного «Лекцию прочитает». То, что автор уже есть на «Элементах», этого абзаца не отменяет: биография «Элементов» в тексте не дублируется (она в блоке «Об авторе»), а описание из источника остаётся. Повод: прототип `YuGeo-261024-syomka-zemli-iz-kosmosa` вышел без этого абзаца. Зафиксировано: `event-description` разд. 3в п. 2, ПАМЯТКА.md разд. 4б.

Зафиксировано: `reference/lectories.md` (карточка лектория), `reference/extra/yunogo-geografa.md`.

Вводное/программное предложение источника над аннотацией (после `<KLBLOCK>`, до `<blockquote>`) — правильное место; выделять его целиком жирным не обязательно. Это объяснение логики, не жёсткое правило; зафиксировано в `event-description` разд. 3в, `post-check` п. 7.
- **Бережное расходование прогонов валидатора (правило 28.09.2026)**: перед показом прототипа валидатор прогоняем МАКСИМУМ два раза — первый прогон сразу после записи прототипа (или после `--fix`), финальный после всех правок. Не гонять валидатор повторно для каждого мелкого исправления: правим все ошибки одним заходом (механику nbsp/«ё»-инвариантов/тире может исправить сам валидатор режимом `--fix`, см. раздел 4б памятки). Старые прототипы (уже загруженные на сайт) валидатором не проверяются и не трогаются.

- **Шапка без дубля площадки и карта обязательна (правило пользователя 19.10.2026, прототип TP-4201984)**: (1) второй абзац шапки описания НЕ дублирует площадку/город из первого абзаца — «Лекция X «Название» в КЦ «Покровские ворота»» при первой строке «…, Москва, КЦ «Покровские ворота»» — дубль, хвост «в …» убираем (цикл/фестиваль типа «в рамках Фестиваля NAUKA 0+» дублем не считается); (2) пропуск ссылки на КАРТУ в блоке адреса при офлайн-части — ошибка: нет точной ссылки — берём карточку лектория/опубликованный образец «Элементов» той же площадки, иначе поисковая ссылка Яндекса с пометкой `(ЗАМЕНИТЬ!)` — но карту не опускаем никогда; вместе с первым прототипом новой площадки карточка лектория создаётся СРАЗУ с готовой ссылкой (для КЦ «Покровские ворота» — карточка и карта от 433664 в `reference/lectories.md`). Зафиксировано: `event-description` разд. 3 п. 2 и разд. 5а, `post-check` п. 9 и 11, ПАМЯТКА разд. 4б.

- **Правило важнее старого образца (правило 30.09.2026)**: опубликованная страница «Элементов» — это образец ВО оформления, но НЕ источник правил: если образец противечит действующему правилу — пишем по правилу (напр. **«Проезд: метро «…»»** — без «до станции метро»; возраст и аннотация — только в фолде 12), и **если правило однозначно — вопрос пользователю не задаём**. Зафиксировано: `event-description` разд. 3в, `proofreading` разд. 1а, `post-check` п. 11, ПАМЯТКА разд. 4б.

Рабочие параметры НЕ трогаем (`?p=`, `?page_id=`, `?agent_id=`, `?text=` в картах, `?period=m`, `?42`); при сомнении — спросить пользователя. Подчищены 7 прототипов ВСмысле; `build.py` чистит такие параметры и при выводе ссылок (`clean_url`/`clean_links`), так что старый «хвост» из `data\events.json` на сайт не попадает. Зафиксировано: `event-description` п. 10, ПАМЯТКА разд. 10.

- **Порядок событий на сайте = порядок на «Элементах» (правило 01.10.2026)**: ключ сортировки — дата, время начала, затем поле `ord` (номер события внутри своей пары «дата+время», в порядке афиши «Элементов»). Логика в `orderlib.py`, используется `scrape.py` и `build.py`; `scrape.py` пересчитывает `ord` по афише при каждой загрузке, ловит перестановки «Элементов» (`order_changed` в отчёте, панель, подпись коммита) и проверяет порядок в файле. Проверка: `python -X utf8 tools\check_events_order.py`. Сырую позицию в афише (`pos`) в `data\events.json` не писать; смена `ord` не является «изменением события». ПАМЯТКА разд. 6а.

- **Иностранные валюты в цене пишем КОДОМ, а не знаком (правило пользователя 15.10.2026)**: на сайте и в Телеграме знак валюты (₪, €, ₸ и т.п.) заменяем кодом — шекель → «NIS», беларуский рубль → «BYN», тенге → «KZT», евро → «EUR», фунт → «GBP» и т.д. (российский рубль остаётся «руб.»). Повод: событие «Крылатая история Израиля» (450708) с ценой «60 ₪». Распознавание цены — `scrape.py` (`foreign_price`, таблица `FOREIGN_CURRENCIES`; словесные обозначения «шекель/тенге/евро…» ищутся только рядом с ценовым словом, чтобы не спутать с прозой); замена знака на код при выводе — `build.py` (`CUR_SIGN`/`fix_currency`, используется в `price_txt` и `render_memo`). Новую валюту добавляют в обе таблицы (`scrape.py` и `build.py`). ПАМЯТКА разд. 12.

- **Валюта цены должна соответствовать стране события (правило пользователя 15.10.2026)**: цена не в рублях обязана быть в валюте страны, где проходит событие. Повод: у лекции «День науки» (450719, Санкт-Петербург) вышла цена «2 USD» — распознаватель принял оборот прозы «бюджет $ 2 млрд» из аннотации за цену. Реализовано в `scrape.py`: `event_currency(city, place)` по полям города/площадки определяет валюту страны (таблица `LOCATION_CURRENCY`; незнакомое место = Россия → рубль), `foreign_price(text, country_cur)` принимает иностранную цену только в этой валюте, а обороты-«множители» («млрд/млн/тыс/billion…» — `_MAGNITUDE`) отсекаются отдельно. Детерминированная проверка — `python -X utf8 tools\check_prices.py` (читает `data/events.json`, запускается и в конце `scrape.py`, вывод «ПРОВЕРКА ЦЕН»). ПАМЯТКА разд. 12.

- **Вуз без указанной цены = бесплатно (правило пользователя 15.10.2026)**: если событие проходит в вузе (площадка/город содержит «университет», «МГУ», «СПбГУ», «ВШЭ» … — список `UNIVERSITY_MARKERS` в `scrape.py`) и цена в источнике не указана, событие считаем бесплатным. Пример: семинар в Европейском университете (450726) был без цены → «Бесплатно». Если цена в источнике есть — она и остаётся. ПАМЯТКА разд. 12.

- **Аудитория — не в шапке описания, и nbsp ПЕРЕД числом-номером (правило пользователя 15.10.2026, прототип TP-4245178)**: в первом абзаце шапки описания номер аудитории/зала НЕ указываем — только город и площадка («… Санкт-Петербург, Европейский университет и&nbsp;ОНЛАЙН.»), номер живёт в поле 13 «Адрес» и в «Доп. информации». Если аудитория где-то упомянута, число — это её номер, номер принадлежит слову ДО числа, поэтому nbsp ставим ПЕРЕД числом: «аудитория&nbsp;217 и&nbsp;ОНЛАЙН», а НЕ «аудитория 217&nbsp;и&nbsp;ОНЛАЙН». Зафиксировано: `event-description` (структура описания п. 1), `proofreading` п. 2, `post-check` п. 3 и 9, ПАМЯТКА разд. 4б.

- **Адрес берём ПО ИСТОЧНИКУ события (правило пользователя 15.10.2026, прототип TP-4245178)**: если на странице события указан адрес — даём именно его, а не «примирённый»/юридический и не из образца «Элементов». Разные источники могут называть одну и ту же площадку по-разному (юридический адрес vs адрес входа; напр. ЕУСПб — Timepad «Шпалерная, 1» против сайта «Гагаринская, 6/1, вход со Шпалерной, 1»: это одно здание), а у разных аудиторий одной площадки — разные адреса. Поэтому адрес «по умолчанию» из карточки лектория подставляем ТОЛЬКО когда в источнике адреса нет. Зафиксировано: `event-description` (поле 13 и разд. 5а), `post-check` п. 11, EUSP-образец `reference/extra/eusp.md` и карточка в `reference/lectories.md`, ПАМЯТКА разд. 4б.

- **Название организации — ПЕРЕД аудиторией/залом/кабинетом (правило пользователя 15.10.2026, ко ВСЕМ лекториям)**: внутри адреса сначала называем организацию, и только потом зал/аудиторию/кабинет: «Омск, набережная Тухачевского, 14, Омский государственный педагогический университет, аудитория&nbsp;432.», а НЕ «…, аудитория&nbsp;432. Омский государственный педагогический университет.» Так номер аудитории привязан к организации (зданию). ИСКЛЮЧЕНИЕ: когда указан этаж/аудитория и организация целиком помещается на этом этаже/в этом помещении (небольшое заведение, а не университет с корпусами), — организация может идти после помещения. Зафиксировано: `event-description` (поле 13 и разд. 5а), `post-check` п. 11, ПАМЯТКА разд. 4б.

- **Чисто-онлайн событие — время с пометкой «(мск)» (правило пользователя 20.10.2026, прототип TP-4258079)**: если событие проходит ТОЛЬКО онлайн (нет офлайн-площадки), время указываем с добавлением «(мск)» — это касается шапки описания, поля 2 «Дата события», поля 2.2 «Время начала» и поля 7 «Дата и время». Пример: «Четверг, 22&nbsp;октября 2026&nbsp;года, 20:00–21:30 (мск), ОНЛАЙН.».
