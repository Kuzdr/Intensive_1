# Пост-проверка описания события

Быстрая финальная проверка ГОТОВОГО описания (прототипа), запускается
 ОТДЕЛЬНЫМ проходом ПОСЛЕ того, как текст уже составлен по скиллу
 `event-description` и вычитан по скиллу `proofreading`. Задача — поймать
 только то, что реально может быть неверным в собранном тексте, и не
 «вычитать всё заново».

 ОБЯЗАТЕЛЬНО для каждого прототипа перед показом пользователю (см. также
 AGENTS.md): самопроверка по `proofreading` (п. 0) + этот пост-проверка.
 Пропускать проходы нельзя — оба скилла содержат правила, но правила не
 срабатывают «сами», их надо выполнять. Проходы идут по очереди, каждый
 со своим письменным артефактом-аудитом (для «ё» и nbsp), см.
 `proofreading` п. 0, п. 5.

 28.09.2026: проверка и `post-check`, и `proofreading` выполняются по
 ГОТОВОМУ тексту как ОДИН сквозной проход «корректура + пост-проверка»,
 каждый со своим письменным артефактом. Экономный протокол (бережное
 расходование прогонов валидатора, см. AGENTS.md): валидатор запускается
 максимум два раза — первый сразу после записи прототипа (можно сразу с
 `--fix`: механику nbsp/«ё»-инвариантов/сущностей тире скрипт исправит
 сам), финальный после всех правок. Ошибки, которые остаются после `--fix`
 (наводки, «ё» по списку yo_words, кавычки, лапки, римские цифры),
 исправляем ОДНИМ заходом и только потом перепрогоняем. Механические
 правки какого-то одного фрагмента не требуют перепрогона между ними.

Проверяем ТОЛЬКО перечисленное ниже. Если пункт не применим (нет такого
элемента в тексте) — помечаем «—» и идём дальше. Не выдумываем правки:
если сомнение, ставим вопрос пользователю в том же блоке.

ИСКЛЮЧЕНИЕ (правило 01.10.2026): пункты про nbsp/«ё»/тире НЕ
применяются к фрагментам, перечисленным в `verbatim_fragments` прототипа —
это дословные вставки готовых блоков с «Элементах» («простое правило
вырезания кода и вставки его в описание»). Их заново не вычитываем и не
переоформляем; валидатор по ним тоже ничего не выводит. На все остальные
тексты прототипа чек-лист действует полностью.


 ## Чек-лист (порядок строго по пунктам)

 0. **Детерминированный валидатор** — прогоняем САМ файл прототипа, а не
    вручную собранный текст:
    `python -X utf8 tools\check_proto_json.py data\prototypes\<папка>\prototype.json`
    (без аргумента — проверяются все прототипы сразу).
    Ручной временный файл допустим только когда прототип ещё не сохранён на
    диск; как только файл есть, проверяем его.
    Валидатор ловит МЕХАНИКУ правил nbsp/«ё»/тире/кавычек и не зависит от
    «внимательности». Он проверяет целиком `prototype.json`: формальное
    поле 1 («Привязка»), названия, аннотацию, текст лектора, HTML описания
    и «Дополнительной информации», имя и описание авторов.
    Если он выдал ОШИБКИ — сначала исправить их в тексте, затем прогнать
    заново, и только потом продолжать чек-лист. Вывод валидатора (итоговый,
    с нулём ошибок) привести в блоке результата.
    Механические ОШИБКИ nbsp/тире можно исправлять самим валидатором
    (бережное расходование прогонов, 28.09.2026):
    `python -X utf8 tools\check_prototype.py --json data\prototypes\<папка>\prototype.json --fix`
    — скрипт сам применит автоправки (nbsp после однобуквенных, удаление
    nbsp после двухбуквенных, числа, тире, инициалы, «ё»-инварианты
    «пойдёт»→«пойдет», сущности тире) и затем выведет отчёт по
    ИСПРАВЛЕННОМУ тексту. После `--fix` остаются только наводки и
    человеческие случаи — правим их ОДНИМ заходом и ещё раз не прогоняем
    до финала. Валидатор на прототип запускаем максимум два раза: после
    записи (можно с `--fix`) и после всех правок.
     Валидатор запускаем на ПОЛНЫЙ прототип — этот прогон и есть
     обязательный перед показом пользователю.
     ДЛЯ ТОЧЕЧНЫХ ПРАВОК (правило пользователя 01.10.2026) есть частичный
     режим `--only`: правка конкретных полей не требует полной
     пересборки текста и полной проверки — проверяем и пересобираем
     ТОЛЬКО изменённые поля:
     `python -X utf8 tools\check_proto_json.py data\prototypes\<ID>\prototype.json --only desc`
     `--only 3,6,13` — по номерам полей, `--only extra --fix` — автоправки
     только в выбранном блоке. Области: fields/поля, title/заголовок,
     annot/аннотация, lecturer/лектор, desc/описание/текст, extra/доп,
     authors/авторы; можно смешивать с номерами (`--only desc,7.4`).
     Частичный прогон НЕ заменяет полный: пометка «ЧАСТИЧНАЯ ПРОВЕРКА» в
     выводе означает «это рабочий прогон, финальный — полный».
     Наводки (НО ВАЖНО: «nbsp между обычными словами (название
    организации?)», прямые кавычки, «не дописан ведущий ноль в дате поля 1»)
    — проверить вручную по правилам ниже.


 1. **Все неразбиваемые пробелы** (`&nbsp;`/`&#160;`/U+00A0): для каждого —
    есть ли правило, требующее его появления? Если правила нет — пробел
    убрать (поставить обычный).
    В частности, не должно быть неразбиваемых пробелов между двух- или
    трехбуквенным предлогом и следующим за ним словом, между обычными 
    словами в названиях организаций.
    Примеры названий: «Фундаментальная библиотека МГУ 
    им.&nbsp;М.&nbsp;В.&nbsp;Ломоносова» — обычные пробелы между словами
    названия, nbsp ТОЛЬКО внутри «им.&nbsp;М.&nbsp;В.&nbsp;Ломоносова»
    (инициалы); НЕ «библиотека&nbsp;МГУ». «Прямая речь» — без nbsp внутри.
    Правильный формат неразбиваемого пробела — только `&nbsp;`.
    ВАЖНО (28.09.2026): в файле прототипа НЕРАЗРЫВНЫЙ ПРОБЕЛ ВСЕГДА пишется
    текстом `&nbsp;` — и в HTML, и в обычных полях. Сырой символ U+00A0 в
    данных запрещён (его ловит валидатор). Пробелы ИСТОЧНИКА образцом не
    являются: nbsp ставится и убирается строго по правилам, поэтому п. 1 и
    п. 2 проверяются ВМЕСТЕ, в обоих направлениях.

2. **Проверка наличия необходимых неразбиваемых пробелов**. ВАЖНО:
    проверяется НЕ ТОЛЬКО текст описания и его HTML-код, но и ФОРМАЛЬНЫЕ
    ПОЛЯ (текст и HTML-код каждого поля) — те же правила.
 2.1. **Тире** (`—`, U+2014): перед каждым тире стоит неразбиваемый пробел?
   После тире — обычный пробел (НЕ nbsp). Тире-интервалы (`–`, U+2013
   между числами/временем) — nbsp вокруг НЕ ставятся, это не тире.
2.2. **Инициалы**: есть ли в тексте инициалы? Оформлены ли они правильно:
   неразбиваемый пробел между инициалами и между инициалом и фамилией
   (например, `Д.&nbsp;Баранов`, `В.&nbsp;В.&nbsp;Маяковский`)? Если
   между инициалами или инициалом и фамилией обычный пробел — заменить
   на nbsp. Обратная проверка: нет ли nbsp там, где это НЕ инициалы
   (например, в «им.», в сокращении перед словом, где nbsp не нужен).
2.3. **Сокращения с точками** (`т.&nbsp;к.`, `и&nbsp;т.&nbsp;п.`,
    `т.&nbsp;е.`, `к.&nbsp;ф.&nbsp;н.` и т.п.): есть ли они в тексте?
    Если да — стоят ли неразбиваемые пробелы ВНУТРИ сокращения (между
    буквами с точками)? Если нет — поставить. Обратная проверка: нет ли
    nbsp ПОСЛЕ последней точки сокращения перед следующим словом (там
    обычный пробел, если это не однобуквенный предлог/союз).
 2.4. **Адресные сокращения**: «г.», «д.», «ул.», «корп.», «стр.» и
    «им.», «пер.», «пл.», «пр-т». Между сокращением и следующим
    словом/числом должен стоять nbsp: «г.&nbsp;Москва»,
    «д.&nbsp;1», «ул.&nbsp;Тверская», «корп.&nbsp;2». НЕ «д.1» слитно
    и не «д. 1» с обычным пробелом.
3. **Числа, включая римские цифры** -- нужны ли перед ними или после них
   неразбиваемые пробелы, и если да, стоят ли они? Исключение (записано
   пользователем 26.09.2026): в формальных полях 2.1 «Начало события»,
   2.3 «Поставить», 2.4 «Снять» nbsp после числа НЕ ставим — обычный
   пробел: «01 октября 2026». Валидатор (п. 0) такие даты пропускает,
   вручную тоже не помечаем.
   НОМЕР аудитории/зала/кабинета («аудитория 217», «зал 12») — число
   принадлежит слову ДО него, поэтому nbsp ставим ПЕРЕД числом:
   «аудитория&nbsp;217» (пример 15.10.2026, прототип TP-4245178; ошибка —
   nbsp ПОСЛЕ числа: «аудитория 217&nbsp;и&nbsp;ОНЛАЙН»).
4. **Однобуквенные слова**: это предлог или союз («в», «с», «к», «о»,
   «у», «и», «а»)? Если да — после него должен стоять nbsp. Если это
   НЕ предлог/союз (например, «я», «А» как буква) — nbsp не ставим.
   Проверить и обратное: нет ли nbsp после ДВУХбуквенных предлогов/союзов
   («от», «на», «по», «из», «за», «до» и т.п.) — там обычный пробел.
5. **Все «ё»**: для каждой «ё» — это случай, где «ё» нужно?
    - смыслоразличительная пара («всё»/«все», «нёбо»/«небо», «о чём»/«чем»);
    - в фамилиях и иностранных словах;
    - слова, в которых часто ошибаются («вёшенка», «Мнёвники»);
    - слова из категорий 3–4 файла `tools/yo_words.txt` — «ё» там ВСЕГДА.
    Каждая строка справочного блока валидатора «все «ё» в тексте»
    (п. 0) обязана получить ВЕРДИКТ в аудите прототипа (см.
    `proofreading` п. 0, п. 5): слово, основание из перечисленных выше,
    решение «оставить/убрать/спросить пользователя». Вердикт — строго
    по основаниям, без «похоже уместно», «официальное написание»,
    «устойчивое написание» и без «так в старых прототипах/образцах».
    Обычное слово без оснований (пары нет, не из категорий 3–4) — вердикт
    строго «убрать»; например, глаголы «пойдет», «пройдет», «разберем»
    пишутся через «е» (не «пойдёт/пройдёт/разберём»). Основание «обычный
    глагол → ё обязательна» НЕДОПУСТИМО (урок 26.09.2026, прототип
    TP-4218939). Отдельно: «мертвец» НИКОГДА не через «ё» (ударение на
     последний слог — «мертвЕц», «мертвецА»; правило пользователя
     07.10.2026) — вердикт тоже строго «убрать». Так же «полёт/полётов» →
     «полет/полетов» (обычное слово без пары; правило 15.10.2026, прототип
     0+-261019-Odintsev: «полётов» проскочило на недопустимом основании
     «устойчивое написание» — слова не было ни в `YO_INVARIANTS`, ни в
     `tools/yo_words.txt`; теперь «полёт» в `YO_INVARIANTS`).
    Строка без вердикта — проход НЕ выполнен.
    Если «ё» не нужно — заменить на «е». Если в слове «ё» НЕТ, но оно
    смыслоразличительно (пара есть) — поставить «ё» (и внести в аудит).
    Проверяется и обратная сторона: нет ли слов без «ё» там, где она
    обязательна, — по списку `tools/yo_words.txt` (читаем файл заново
    при каждом проходе) и по всем именам собственным с «е».
    Проверяются и тексты формальных полей.
6. **Слова, парные по «ё»**: «все/всё», «нем/нём», «чем/чём»,
   «звезды/звёзды», «весны/вёсны» и т.п. Каждое вхождение из списка
   `tools/yo_words.txt` (категории 1–2: конкретная форма / все формы)
   проверяем по контексту — в нужном ли варианте оно стоит?
   Например, «нём» в «на нём», «о нём» — ударное местоимение, «ё» НУЖНА
   (пишем «на&nbsp;нём», «о&nbsp;нём»); «нем» без «ё» — это прилагательное
   «нем/немая». «звезды» — род. п. ед. ч., «звёзды» — им. п. мн. ч.;
   «весны» — род. п., «вёсны» — им. п. мн. ч. Решаем по контексту
   и фиксируем решение.
7. **Упоминание имени автора**: для КАЖДОГО упоминания автора в тексте —
   правильно ли оно выделено?
   - имя автора — жирным курсивом (`<b><i>…</i></b>`);
   - описание/регалии автора — курсивом (`<i>…</i>`), без жирного,
     если это не название;
   - нет ли вокруг имени лишних выделений (жирный без курсива, курсив
     без цели);
   - характеристика автора (должность, звание, «орнитолог», «кандидат
     биологических наук») в любом упоминании выделена курсивом (`<i>…</i>`);
   - название фильма/произведения/картины в тексте выделено жирным
     (`<b>…</b>`) (правило 15.10.2026, прототип TP-4254451);
   - **описание автора ИЗ ИСТОЧНИКА** (должность/звание) присутствует в
     тексте описания последним абзацем аннотации, в форме
     «<b><i>Имя Фамилия</i></b>&nbsp;— <i>описание из источника</i>.»
     (без вводного «Лекцию прочитает»)? Если источник его даёт, а абзаца
      нет — это ПРОПУСК (правило 15.10.2026, прототип YuGeo-261024);
      стандартная биография «Элементов» (KLBLOCK) его не заменяет.
    - **несколько авторов — каждому СВОЙ абзац** (правило пользователя
      15.10.2026, ко всем лекториям): если авторов два или больше, описание
      каждого автора — отдельный `<p>…</p>`, а не слитно в одном абзаце.
      Один абзац допустим, только когда источник связывает авторов
      синтаксически (одна общая характеристика на двоих).
 8. **Формальные поля**: нет ли в них шрифтовых выделений (жирный,
   курсив, `<b>`, `<i>`)? В формальных полях выделений быть НЕ должно
   (только `<br>`, `&nbsp;`, кавычки, тире). Если есть — убрать.
 9. **Название лекции в шапке**: что является названием лекции в шапке
   описания? Выделено ли оно жирным шрифтом (`<b>…</b>`)? Если нет —
   выделить. Название в шапке — то, что идёт после «Лекция …», в
   кавычках.
   Плюс проверка ПЕРВОГО абзаца шапки: в нём НЕ должно быть номера
   аудитории/зала (только город и площадка) — правило пользователя
   15.10.2026, прототип TP-4245178; номер аудитории — в поле 13 «Адрес»
   и в «Доп. информации».
 9a. **Вложенные кавычки**: лапки `„…“` допустимы ТОЛЬКО внутри ёлочек
    `«…»`. Проверяем каждое вхождение `„` и `“`:
    - если вокруг есть внешние `«…»` (например, название целиком взято в
      ёлочки, а внутри — цитата) — вложенность правильная, не трогаем;
    - если внешних кавычек НЕТ, а стоят лапки — это ошибка: единственные
      кавычки должны быть ёлочками. Меняем `„слово“` → `«слово»`.
    Особенно проверяем формальное поле 5 «Название лекции»: там название
    приводится БЕЗ внешних кавычек, значит любые кавычки внутри — ёлочки.
    Ошибка из реальной обратной связи (26.09.2026, прототип Gerasimov):
    в поле 5 стояло `Язык, безвластие и космос: „всечеловеческий“ язык`,
    хотя внешних кавычек там нет.
10. **KLBLOCK**: `<KLBLOCK eltclub_authors_about/>` (заглушка блока об
   авторе) стоит на своём месте — сразу после шапки (абзацев шапки) и
   ПЕРЕД `blockquote`-аннотацией? Если KLBLOCK в тексте нет или стоит
   не там — исправить.
11. **blockquote и div**: `<blockquote>` используется ТОЛЬКО для
      аннотации (основного описания события). Никаких других `<blockquote>`
      и `<div>…</div>` в тексте описания быть не должно. Если встретились —
      заменить на обычный абзац `<p>` (или поместить в аннотацию, если это
      её часть). HTML-фрагменты прототипа (описание и «Дополнительная
      информация») выводятся БЕЗ обвязки: ни `<div class="itemblock memo">`,
      ни сепараторов `<div class="cl"></div>` — только внутренние блоки
      (обвязку добавляет сайт).
      «Дополнительная информация»: воспроизводит разметку опубликованных
      страниц — выделения `<b>` («Вход <b>бесплатный</b>», «<b>Открытая
      трансляция</b>», «<b>Адрес:</b>», «<b>Проезд:</b>», «<b>Телефон:</b>»,
      стоимости), разделительный комментарий `<!-- @@@ -->` НЕПОСРЕДСТВЕННО

## Оформление результата

Вывод — ОДНИМ блоком, по пунктам 0 и 1–16, каждый пункт строго
«номер. вывод», без пояснений, если вывод «и/всё ОК»; иначе — краткое
описание найденного и исправления. В конце — отдельной строкой
«РЕЗУЛЬТАТ: …» (например, «исправлений нет» / «исправлено 3»).

Пункт 0 (валидатор) включается в тот же блок первой строкой: показать
его итоговый ответ («ошибок нет» / какие ошибки исправлены и через
сколько прогонов достигнут ноль).

Никакой другой информации (полные тексты, HTML-обвязка) в этом блоке
не выводим.
