# Описание события из источника (нет на «Элементах»)

Задача: по описанию события на сайте организатора или на Timepad собрать
полный «паспорт» события для «Научного календаря». События нет на
elementy.ru, поэтому работа идёт по исходным материалам источника.

В отличие от парсинга «Элементов», описание здесь создаётся С ИСПОЛЬЗОВАНИЕМ
ИИ (не алгоритмически): пользователь даёт текст/ссылки источника, мы по ним
пишем описание, следуя формату ниже. Правила и примеры накапливаются
в этом скилле по мере обучения.

## 0. Порядок работы

1. Пользователь присылает источник (ссылка или скопированный текст — сайт
   организатора, Timepad, страница ВК и т.п.). В дальнейшем нужно будет
   собирать новые события с самих источников.
2. Если есть ссылка — открыть её и взять данные.
3. Собрать «формальные поля» (раздел 2) — отдельным блоком, готовым
   к вставке в админку.
4. Написать текст описания события (раздел 3) с HTML-разметкой как на сайте.
5. Если автора события в данных «Научного календаря» ещё нет — подготовить
   описание автора (раздел 4).
6. Вывести результат в чат (раздел 5): формальные поля, текст с разметкой
   и HTML-код описания.
7. ПЕРЕСОБРАТЬ САЙТ (обязательный шаг): `python -X utf8 build.py` —
   чтобы прототип появился на сайте. Если запущен `serve.py`, его вотчер
   сам пересоберёт сайт при изменении `data/prototypes/*/prototype.json`;
   но пересборку нужно УБЕДИТЬСЯ, что она произошла (вывод build.py
   содержит строку «готово»/список событий). Только после этого прототип
   можно показывать пользователю в собранном виде.
   ПУБЛИКАЦИЯ — по кнопке «Обновить данные» на главной странице
   (локальный `serve.py`): кнопка сама сравнивает прототипы с тем
   состоянием, что уехало на GitHub, и публикует изменившиеся. Поэтому
   после правки прототипа можно просто сказать пользователю: «нажмите
   «Обновить данные»» — публикация произойдёт там. Агент коммит и push
   без отдельной просьбы пользователя НЕ делает.
8. Спорные места (новое поле, неоднозначность) — спросить пользователя,
   потом зафиксировать решение в этом скилле.

## 1. Источники

- Сайт организатора (страница события) — основной источник; иногда может
  быть несколько страниц.
- Timepad — иногда единственный источник, иногда дополнительный, часто 
  именно здесь можно найти ссылку на регистрацию.
- Если данные в источниках расходятся — приоритет у сайта организатора;
  расхождение показать пользователю и спросить.

**Что берём, а что нет (критерий отбора, решение пользователя 01.10.2026).**
Отбор — **по содержанию, а не по формату**: берём научно-популярные события.
Дискуссия, клуб, круглый стол берутся, если по существу научные (например,
дискуссия между учёными); само слово «дискуссия» в названии ничего не решает.
Заведомо ненаучное не берём: книжные и поэтические клубы, «медленное чтение»,
разговоры о романах, театральные клубы, языковые студии и разговорные клубы,
литературные студии, концерты, экскурсии и прогулки без научной части,
тренинги, мастер-классы, практикумы, квесты. Спорные случаи — спросить
пользователя, не решать молча. Список отбора по конкретным лекториям — в
`reference/lectories.md`.

## 1а. УНИВЕРСАЛЬНЫЙ шаблон ответа (все лектории)

Шаблон ответа (формальные поля → текст → HTML, разделы 2–4) ОДИН для всех
лекториев, независимо от того, где беру событие. Нюансы бывают ТОЛЬКО в
разборе источника (разд. 1б), но описание события формируется одинаково. 
«Онлайн», nbsp, ёлочки, KLBLOCK — обрабатываются одинаково везде.

## 1б. Нюансы разбора источника — по лекториям

Различия между лекториями затрагивают ТОЛЬКО то, откуда берём данные и
какие поля есть (формальные поля и структура ответа — единые, см. 1а).

Карточки лекториев — в файле `reference/lectories.md` (по карточке на
лекторий: подзаголовок, ID-правило, онлайн-политика, место по умолчанию,
особенности разбора). При разборе события открыть карточку нужного
лектория и следовать ей. Новые правила лектория записываются сразу
в его карточку, а не дублируются здесь.

Сейчас есть карточки: «Живой город» (Тверь), «Прямая речь» (Москва),
Astrocamp (Москва), Фестиваль NAUKA 0+, «Центр "Архэ"». Другие лектории —
добавляем по мере появления; шаблон ответа при этом НЕ меняем.

## 2. Формальные поля (админка)

Выводятся ОТДЕЛЬНЫМ блоком, БЕЗ номеров и названий полей, но в строгом
порядке. Блок готов к вставке в админку: с `&nbsp;`, `<br>` и т.п.

Порядок полей:
 0. ID события
 1. Привязка (инвертированная дата + индекс времени)
 2. Дата события: дата, город, площадка [и ОНЛАЙН], время
 2.1. Начало события: дата словами вида «03 ноября 2026» (без nbsp после числа)
 2.2. Время начала: только время начала (19:00, 18:30 (мск))
 2.3. Поставить: текущая дата вида «26 сентября 2026» (без nbsp после числа)
 2.4. Снять: следующий день после события («04 ноября 2026») (без nbsp после числа)
 3. Полный заголовок с подзаголовком: подзаголовок(лекторий, цикл и т.п., тип 
    (лекция и т.п.), автор, название (в кавычках);
 4. Полный заголовок без подзаголовка;
 5. Только название лекции (без кавычек);
 6. Подзаголовок (лекторий/организатор/цикл лекций);
 6.1. Тип: по умолчанию «Лекция»; для мероприятия другого типа — значение из
      списка <Тип> (Курс, Фестиваль, Экскурсия и т.п.)
 6.2. Место: из выпадающего списка <Место проведения> на «Элементах»;
      если точной площадки в списке нет — город
 6.3. Лекторий: значение из списка <Лекторий>
 6.4. Тематики: значение(я) из списка <Тематика>
 7. Дата и время;
 8. Место (город, площадка в тексте описания; не путать с полем 6.2);
 9. Источники (URL);
 10. URL регистрации/покупки билета;
 11. Стоимость;
 12. Возрастные ограничения;
 13. Адрес;
    14. Аудитория (по умолчанию «Для всех» — см. ниже).

  Про поле 14 «Аудитория»: на «Элементах» в описании события есть поле
  «аудитория» с вариантами «для всех» / «для ученых» / «для студентов» /
  «для школьников». В источниках про это почти никогда не пишут, поэтому
  по умолчанию ставим «Для всех» (вариант 20495): обычное научно-популярное
  мероприятие открыто всем. Иную аудиторию ставим, ТОЛЬКО если это прямо
  следует из источника: мероприятие для школьников, для студентов, только
  для специалистов/для учёных. Тогда же записываем решение в `notes`
  (в источнике «будет интересно всем» → «Для всех»). Пустым поле не бросаем,
  «—» не выводим.

В формальных полях не бывает выделений жирным и курсивом, но бывают <br> и &nbsp;.

 В формальных полях используем КОРОТКИЕ наименования организаций
 (например, «Фундаментальная библиотека МГУ»), в первом абзаце шапки
 описания — ПОЛНЫЕ («Фундаментальная библиотека МГУ им.&nbsp;М.&nbsp;В.&nbsp;Ломоносова»).
 nbsp внутри названия организации НЕ ставим (обычные пробелы), кроме
 стандартных случаев (инициалы, числа, однобуквенные предлоги).

Формальные поля выводятся ПОСЛЕДОВАТЕЛЬНО, в двух видах (не колонками):
- для чтения: каждое поле в отдельном абзаце, с названием поля, внутри
  абзаца выводится содержимое (<br> заменяется переводом строки,
  &nbsp; пробелом);
- для копирования: в блоке кода, каждое поле на новой строке, БЕЗ названий
  полей — только значения, готовые к вставке в админку (с &nbsp;, <br>).


Пример (лекция «Нейробиология боли», lectory2.ru):

```
2026.09.196
19.09.2026, Тверь, Филармония, 18:00
19 сентября 2026
18:00

20 сентября 2026
Лекторий «Живой город»<br>Лекция Владимира Алипова «Нейробиология боли»
Лекция Владимира Алипова «Нейробиология боли»
Нейробиология боли
Лекторий «Живой город»
Лекция
Тверь
Лекторий «Живой город»
Нейробиология
Суббота, 19 сентября 2026&nbsp;года, 18:00
Тверь, Филармония
https://lectory2.ru/#lecture_967
https://lectory2.ru/#lecture_967
1400&nbsp;руб.
16+
```

ВАЖНО:
Факт в формальное поле заносится ТОЛЬКО если он подтверждается источником.
Если поле неизвестно — писать «—» и не выдумывать.

ВАЖНО про поля 2.1–2.4 и 6.1–6.4: значения этих полей берутся ТОЛЬКО из
списков админки «Элементов» (см. разд. 2, поле 6.4): актуальные списки
«Тип», «Аудитория», «Место проведения», «Лекторий», «Тематика» лежат в
`reference/lists/*.md` (type.md, audience.md, place.md, lectorium.md,
theme.md). Списки снимаются со страницы события elementy.ru (на /events
они урезаны до текущей выдачи) скриптом `tools/update_admin_lists.py`.
Список «Место проведения» обновляется часто — перечитываем его раз в день
(расписание — workflow `update-admin-lists`, локально — команда
`python -X utf8 tools/update_admin_lists.py`) и по требованию пользователя.
Значения вставляем ДОСЛОВНО из списка (например, «Москва, Научно-популярная
библиотека «Научка»»).

ВАЖНО про полноту списков и безопасность обновления:
- Селект «Место проведения» на странице события может быть УРЕЗАН (на
  страницах других лекториев — 26–32 значения). Полный набор площадок
  лектория виден на странице события ЭТОГО лектория (пример: все 8
  площадок ВДНХ — на архивной странице события 449960). Если значение
  площадки не нашлось в списке — снимаем селект вручную и дописываем его в
  `reference/lists/place.md` отдельным блоком «ДОПОЛНЕНИЕ от <дата>», не
  перезаписывая файл.
- `tools/update_admin_lists.py` ПЕРЕЗАПИСЫВАЕТ файлы `reference/lists/*.md`,
  а не дополняет их. Перед запуском — копия файлов (или `git stash`), иначе
  прежние значения теряются (30.09.2026 так были потеряны 900+ площадок,
  восстановлено через `git checkout`).

## 3. Текст описания и HTML-разметка (как на сайте)

В выводимый HTML-фрагмент обвязка НЕ включается: ни
`<div class='itemblock memo'>`, ни сепаратор `<div class='cl'></div>` —
только внутренние блоки (шапка, KLBLOCK, blockquote, при необходимости
цена/ссылки).

Подробнее о формальных полях:

0. Идентификатор события, присваиваемый ему в начале работы в зависимости от источников,
   URL на них и id на источнике (если есть). Если источник — Timepad: TP-<id Timepad>
   (например, TP-4161306);
 1. **Привязка:** поле начинается с инвертированной даты через точки, например, для 19
    сентября 2026: 2026.09.19; в конце приписываются 1 или 2 цифры, без пробела.
    ПЕРВАЯ цифра — по часу начала события: 12 часов и раньше — 0, 13 — 1, 14 — 2,
    … 20 — 8, 21 час и позже — 9.
    ВТОРАЯ цифра (минуты) ставится ТОЛЬКО если время начала попадает в диапазон
    13:00–20:59 И минуты не равны 00: до :30 — 4, ровно :30 — 6, после :30 — 8.
    Вне диапазона 13:00–20:59 минуты в привязке НЕ участвуют (никакой второй
    цифры), даже если минуты заданы.
    Например, в указанную дату: 19:00 — 2026.09.197; 19:30 — 2026.09.1976;
    19:45 — 2026.09.1978; 11:30 — 2026.09.190; 09:30 — 2026.09.190; 22:45 — 2026.09.199.
    Для 29 сентября 2026 в 19:00 — 2026.09.297.
    Поле 1 обязательно: если время начала известно, «Привязка» выводится всегда,
    и её значение сверяется детерминированно (см. разд. 5б).

2. **Дата события:** через запятую дата (дд.мм.гггг), город, площадка (если есть
   онлайн-трансляция, добавляется без запятой "и ОНЛАЙН"), время начала события
   (без времени окончания). Если мероприятие проводится ТОЛЬКО онлайн —
   после времени начала дописать часовой пояс: «29.09.2026, ОНЛАЙН, 18:30 (мск)».
   Часовой пояс указываем В ЭТОМ поле и только в нём (в других полях не дублировать).
   Поле переименовано из «Время и место» по решению пользователя (26.09.2026);
    содержание не изменилось.
2.1. **Начало события:** дата словами, число с ведущим нулём, месяц — слово в
     родительном падеже, год цифрами: «03 ноября 2026». Суффикс «года» не
     добавляем. В этом поле nbsp после числа НЕ ставим (обычный пробел:
     «01 октября 2026») — записано пользователем 26.09.2026, см. «Историю
     правил». Дублирует дату поля 2, но в другом формате (для админки «Элементов»).
2.2. **Время начала:** только время начала события — «19:00». Если мероприятие
     ТОЛЬКО онлайн — «18:30 (мск)». Часовой пояс — только здесь (и в поле 2,
     см. выше). Время окончания не указываем.
2.3. **Поставить:** дата «постановки» (текущая дата работы над событием) словами:
     «26 сентября 2026». nbsp после числа НЕ ставим (как в поле 2.1).
2.4. **Снять:** дата «снятия» — следующий день после события, словами:
     событие 03.11.2026 → «04 ноября 2026». nbsp после числа НЕ ставим
     (как в поле 2.1).
3. **Полный заголовок с подзаголовком:** подзаголовок -- название лектория, цикла
   лекций и т.п. (если есть); после подзаголовка <br>; тип мероприятия
   (лекция, фестиваль, экскурсия и т.п.); если лекция, автор в родительном падеже 
   (лекция Сергея Попова), если другое мероприятие, может быть другой формат
   (например, встреча с Сергеем Поповым); название в кавычках.
   ВАЖНО: формат этого поля не такой, как у похожей на него второй строки шапки описания. 
   Здесь подзаголовок всегда в начале, в именительном падеже и отделяется <br> 
   (а там в конце и синтаксически связывается с названием)
4. **Полный заголовок без подзаголовка:** то же, но без подзаголовка. 
   Если подзаголовка нет, совпадает с предыдущим полем.
5. Только название лекции (без кавычек);
6. **Подзаголовок** (лекторий/организатор/цикл лекций); тот же, что в поле 3.,
   может отсутствовать, тогда прочерк.
 6.1. **Тип:** по умолчанию «Лекция». Если событие другого типа (курс, фестиваль,
     экскурсия и т.п.) — значение из списка `<Тип>` (`reference/lists/type.md`),
     дословно (например, «Курс», «Фестиваль», «Экскурсия»). Для лекции из КУРСА
     ставим «Курс» (решение пользователя 26.09.2026).
     НЕСКОЛЬКО ЛЕКЦИЙ В ОДНОМ СОБЫТИИ тип НЕ МЕНЯЮТ (уточнение пользователя
     29.09.2026): вечер из трёх лекций — это «Лекция». Если источник ПРЯМО
     называет событие фестивалем и т.п. — добавляем ВТОРОЙ тип, а «Лекция»
     остаётся; если источник ничего не называет — просто «Лекция» и решение
     пишем в `notes`.
6.2. **Место:** значение из выпадающего списка `<Место проведения>` на
     «Элементах» (`reference/lists/place.md`), дословно, с учётом уровня
     вложенности — например, «Москва, Научно-популярная библиотека «Научка»».
     Если точной площадки в списке нет (маленький город и т.п.) — берем город
     (например, «Тверь»). Список часто обновляется: перечитывать раз в день
     по расписанию и по требованию (см. разд. 2, «ВАЖНО про поля 2.1–2.4»).
     Поле 6.2 — для админки (выбор из списка); НЕ путать с полем 8 «Место»,
     которое является текстом описания.
6.3. **Лекторий:** значение из списка `<Лекторий>` (`reference/lists/lectorium.md`),
     дословно, например «Лекторий Культурно-просветительского центра «Архэ»».
     Если в списке нет — ставим «—».
6.4. **Тематики:** значение(я) из списка `<Тематика>`
     (`reference/lists/theme.md`), обычно 1–3 значения, соответствующих
     тематике события; подбираем по содержанию (например, для лекции о боли —

### 3в. Правила, зафиксированные пользователем 28.09.2026 (прототип СПбГУ)

Обязательны для каждого нового прототипа:

1. **«Прочитает», а не «прочтёт/прочтет».** Глагол прочтения в описании ВСЕГДА
   пишем «прочитает», даже если в источнике «прочтет». «ё» в нём не нужна
   (см. список причин в `proofreading` п. 1).
2. **Об авторе — один раз, и в КОНЦЕ аннотации.** Абзац с представлением
   автора («Лекцию прочитает <b><i>Анна Антонова</i></b>, <i>старший
   экскурсовод…</i>») ставится ПОСЛЕДНИМ абзацем аннотации, а не в её начале
   (уточнение пользователя 30.09.2026). Сам текст лекции идёт раньше.
   Представление автора даётся ОДИН раз: в этом абзаце. Других упоминаний
   автора с должностью/регалиями в аннотации не делаем. Если формат
   представления источника другой (например, «Лекцию прочитает …, а
   расскажет …»), приводим к той же схеме: имя жирным курсивом, должность
   курсивом.
3. **Вложенные кавычки в первом абзаце.** Полное название лекции — целиком в
   «ёлочках», а его внутренняя часть — в „лапках“:
   «<b>„Эпоха дворцовых переворотов“ — время безликих или незаслуженно
   забытый период истории России?»</b>». Баланс проверяем целиком: «ёлочки»
   закрываются в самом конце названия, «лапки» — вокруг внутренней части.
   Даже если в источнике кавычки стоят иначе.
4. **Онлайн и формат — в описание.** Если источник пишет, что лекция пройдёт
   онлайн, с переводом, на другой площадке и т.п., эта фраза идёт в АННОТАЦИЮ
   («Лекция пройдет онлайн на русском языке с синхронным переводом на
   испанский.»), а не только в «Дополнительную информацию». В
   «Дополнительной информации» остаются ссылка на регистрацию, источники,
   адрес и способы связи.
5. **Организатор прототипа — по источнику.** Для фильтра «Организаторы» на
   сайте организатор определяется сайтом или Timepad-аккаунтом, из которого
   взята лекция (см. разд. 5в). Поле 6.3 «Лекторий» при этом может быть
   прочерком: для СПбГУ пользователь разрешил написать полное название
   «Санкт-Петербургский государственный университет», даже если в списке
   админки такого значения нет.
6. **Название лекции — обычный текст, «ё» в нём НЕ выключается** (ошибка
   пользователя 30.09.2026, прототип TP-4190696 «Нарисованные звёзды»).
   Основания вида «название из источника», «так в афише», «так на Timepad»
   НЕ являются доводом: проект правит букву «ё» по своим правилам в любом
   своём тексте, включая заголовок, поле 5 «Название события» и аннотацию
   карточки. На «Элементах» это событие опубликовано как «Нарисованные
   звёзды» — то есть «ё» в названии требуется, а не запрещено.
   Обратное тоже верно: `ё` не пишется там, где она не нужна по правилам
   проекта (слово-инвариант, разговорное слово) — независимо от источника.

ВАЖНО: текст описания НЕ сокращаем и НЕ переписываем без надобности.
Переносим из источника(ов) ВСЁ существенное: все абзацы, все пункты
списков, подзаголовки, формулировки. Ничего из источника не теряем.
Допустимо только то, что прямо предписывают правила проекта
(например, включить подзаголовок в начало текста) — и тоже без потери
смысла.

В описании используются только абзацы <p> и списки <ul><li>. Тег <blockquote>
используется только для оформления аннотации в целом. Если в источнике 
используются другие теги (<blockquote>, <div>), они преобразуются в 
обычные абзацы.

Технические поля (как попасть на мероприятие, необходимость регистрации,
трансляция и т.п.), адрес с проездом, способы связи и ссылки на источники
выносим в раздел «Дополнительная информация» (см. разд. 5а).

Подзаголовок (лекторий/цикл и т.п.) из источника — НЕ теряем: включаем
или в заголовок, или в текст описания (обычно лучше в текст, и хорошо —
сразу после блока об авторе). Не выбрасываем его только потому, что он
уже есть в шапке.

**простым правилом: вырезать код и вставить его в описание**. Никаких
«примерок» типографики, переписывания, «улучшения» и повторных согласований
ради nbsp/ё НЕ делаем: готовый текст — источник истины.

Как это работает на практике:
1. Открываем готовое событие автора/организатора на «Элементах», копируем
   нужный HTML-дословно.
2. Вставляем его в блок автора (`block_html`, поля 7.3/7.4).
3. В `data/prototypes/<ID>/prototype.json` перечисляем эти вставки в поле
   верхнего уровня `verbatim_fragments` (массив строк). Обычно их 2: форма
   именительного падежа (блок автора, поле 7.4) и форма, вписанная в
   предложение описания (родительный падеж в аннотации).
4. Валидатор `tools/check_prototype.py` по `verbatim_fragments` пропускает
   проверки nbsp/«ё»/тире внутри этих фрагментов — готовое оформление
   «Элементов» не ломается. Режим `--fix` их тоже НЕ правит (исправлено
   29.09.2026: он раньше вставлял nbsp внутрь готового блока и ломал
   дословность; регрессия закреплена в `tools/check_skills.py`).
5. Фрагмент должен СОВПАДАТЬ с текстом в прототипе ПОБАЙТОВО (регистр,
   пробелы, `&nbsp;`) — иначе вхождение не находится и правила сработают
   как обычно. Если один и тот же блок вставлен в разных формах — заносим
   КАЖДУЮ форму отдельным элементом.

Пример (`verbatim_fragments`):
```json
"verbatim_fragments": [
  "Ведущий экскурсовод центра «Космонавтика и авиация», историк космонавтики, автор экскурсий и квестов, автор телеграм-канала «Я&nbsp;записал»",
  "ведущего экскурсовода центра «Космонавтика и авиация», историка космонавтики, автора экскурсий и квестов, автора телеграм-канала «Я&nbsp;записал»"
]
```

ВАЖНО: это правило НЕ отменяет `proofreading`/`post-check` для текста,
который пишем мы сами (аннотация, шапка, доп. информация, формальные поля) —
там все правила проекта действуют в полном объёме.

## 3а. Лекции курсов (цикл лекций)

Описание лекции из КУРСА (цикла лекций) отличается от обычной лекции:

1. Во второй строке шапки, перед блоком «об авторе» (KLBLOCK), указываем
   название КУРСА, а не лекции (образец — «Элементы», 449663, первая
   лекция курса Квартальнова):
   `<p>Культурно-просветительский центр «Архэ» приглашает на курс
   <b><i>Павла Квартальнова</i> «Зимняя экология: снег, холод и&nbsp;тепло»</b>.</p>`
2. После блока «об авторе», перед аннотацией — ОБЯЗАТЕЛЬНЫЙ абзац
   с названием лекции: «продолжим говорить о...» (для непервой лекции)
   или «Тема первой лекции: <b>«Название лекции»</b>». Перед ним сразу
   KLBLOCK; далее аннотация в «ёлочках».
3. В конце аннотации, перед закрывающим `</blockquote>`, добавляется
   ПЛАН КУРСА — нумерованный список `<ol><li>…</li>…</ol>` с номерами
   лекций и их темами (и датами, если известны).
4. ТОЛЬКО у первой лекции курса указывается стоимость курса в целом
   (и, если есть, цена подписки на трансляции всего курса); у остальных
   лекций курса это не указывается.
5. ФОРМАЛЬНЫЕ ПОЛЯ 3–6 у лекций курса (схема записана пользователем
   26.09.2026 при прототипе Усанова, TP-4206645):
   - поле 3 (полный заголовок с подзаголовком):
     «Название лекции»<br>Лекция N курса Автора «Название курса»
   - поле 4 (полный заголовок без подзаголовка):
     «Название лекции». Лекция N курса Автора «Название курса»
   - поле 5 (только название): Название лекции (без кавычек)
   - поле 6 (подзаголовок): Название курса. Лекция N
   Номер — цифрой, неразбиваемый пробел ПЕРЕД ним: «…Лекция&nbsp;1».
   Число относится к одному соседнему слову — к «Лекция» (nbsp ставлю
   только перед числом), поэтому после числа — обычный пробел:
   «Лекция&nbsp;1 курса…», НЕ «Лекция&nbsp;1&nbsp;курса».
   Пример для курса «онлайн-курс Павла Усанова» (первая лекция
   «Великобритания. Как маленький остров изобрел Промышленную
   революцию»):
   - поле 3: «Великобритания. Как маленький остров изобрел Промышленную
     революцию»<br>Лекция&nbsp;1 курса Павла Усанова «„Пять историй
     богатства“: как страны становятся великими и&nbsp;почему теряют свой
     успех»
   - поле 4: «Великобритания. Как маленький остров изобрел Промышленную
     революцию». Лекция&nbsp;1 курса Павла Усанова «„Пять историй
     богатства“: как страны становятся великими и&nbsp;почему теряют свой
     успех»
   - поле 5: Великобритания. Как маленький остров изобрел Промышленную
     революцию
   - поле 6: «Пять историй богатства»: как страны становятся великими
     и&nbsp;почему теряют свой успех. Лекция&nbsp;1
   Кавычки вокруг «Название курса»: у этого курса в названии УЖЕ есть
   «ёлочки» («Пять историй богатства»), поэтому вокруг всего названия
   курса ставим только «ёлочки», а внутренние превращаем в „лапки“
   (см. `proofreading`, п. 3 «Кавычки»). Результат:
   «„Пять историй богатства“: как страны становятся великими
   и&nbsp;почему теряют свой успех». НЕ писать ««Пять историй богатства»»
   (два знака « подряд).
Поле 6 в образцы «Элементов»: «Зимняя экология: снег, холод
    и&nbsp;тепло. Лекция&nbsp;1», «На острие науки. Астрономия
    и&nbsp;современная физика. Лекция&nbsp;5» (449663, 450094).
    В полях 3–6 автор — ТОЛЬКО «Имя Фамилия» (в родительном падеже
    «Фамилия Имя» для «курса …»), БЕЗ характеристик/регалий
    («астрофизика», «профессор» и т.п.). В шапке описания регалия тоже
    не нужна: «приглашает на курс <b><i>Сергея Попова</i> «…»</b>»,
    НЕ «приглашает на курс астрофизика <b><i>Сергея Попова</i>…</b>»

    слово «астрофизика» в полях 3/4 было лишним).

Если нет, запускаем поиск на "Элементах", используя URL:

(подставляем имя и фамилию автора, например, `Алексей+Паевский`).

`Научный календарь  • Анна Хоружая, Алексей Паевский • 19.09`

Если поиск НЕ УДАЛСЯ (сайт недоступен, поисковый провайдер блокирует запрос,

## 5. Формат вывода (в чат)

ПРАВИЛО СООТВЕТСТВИЯ: сначала готовим HTML-код, потом в тексте для показа
выводим его с точностью до согласованных изменений (у абзацев, которые 
предназначены для помещения в однострочные поля, убираем теги абзаца).

HTML-блоки (блоки 2, 4, 6 и блок «Об авторе») выводим ВСЕГДА ПОЛНОСТЬЮ:
без сокращений «…», без пропусков абзацев и пунктов. Если блок уже был
показан и требуется перевывести его (исправление, переспрос) — повторяем
полный блок целиком, а не его фрагмент.

Выводим результат несколькими блоками:

1. **Формальные поля: для чтения** — отдельный блок (раздел 2): каждое поле
  с названием в новом абзаце, внутри абзаца выводится содержимое поля
  (<br> заменяется переводом строки, &nbsp; пробелом)
2. **Формальные поля: для копирования** — в блоке кода, каждое поле на новой
  строке, БЕЗ названий полей, с <br>, &nbsp;
3. **Текст описания** — читаемый вариант с лёгкой разметкой (курсив,
  жирный), без HTML-тегов. Заканчивается на конце аннотации.
4. **HTML-код описания** — только внутренние блоки (без обвязки div):
  шапка, KLBLOCK, blockquote (до `</blockquote>` включительно), — в блоке кода.
5. **Дополнительная информация: текст** — читаемый вариант без тегов:
  трансляция, регистрация/покупка билетов, адрес (и проезд), способы
  связи, ссылки на источники и полезные ссылки (что есть у события).
6. **Дополнительная информация: HTML-код** — те же блоки абзацами `<p>`
  со ссылками и &nbsp;, в блоке кода (как в п. 4, без обвязки div).
7. **Об авторе** (если автора нет).

В блоке 4. (HTML-код описания) вставляем пустые абзацы между всеми абзацами 
 <p> и пунктами списка <li>, тегами блока об авторе <KLBLOCK>, а также сразу
 после открывающего и перед закрывающим тегами <blockquote>. ВНУТРИ <ul>
 пустые абзацы не вставляем: после <ul> и перед </ul> пустая строка НЕ нужна
 (раньше ошибочно ставились). Тот же принцип — в блоке 6 (между <p>
 пустая строка).

 Абзац «Лекцию прочитает …» (указание автора с его ПОЛНЫМ описанием)
 ставим В КОНЕЦ аннотации: последним абзацем внутри <blockquote>, сразу
 перед закрывающим тегом (а не первым абзацем аннотации и не за пределами
 <blockquote>). Сначала смотрим, ЕСТЬ ли в источнике описание автора:
 - описания автора в источнике НЕТ (ни отдельным блоком, ни в тексте) —
   НИЧЕГО не добавляем: текст лекции оставляем как есть, описание автора
   не выдумываем;
 - описание автора ЕСТЬ — отдельным блоком (как «Лекторы/ведущие»
   на фестивале NAUKA 0+) или в самом тексте лекции (например, в конце,
   дублируя упоминания в начале/середине) — в обоих случаях действуем
   как с отдельным описанием, по представленности лектора в тексте:
   • лектор в тексте НЕ упоминался → добавляем закрывающий абзац
     «Лекцию прочитает …» с полным описанием;
   • лектор упомянут с ПОЛНЫМ/достаточным описанием — например,
     «с&nbsp;<b><i>Сергеем Марковым</i></b>&nbsp;— директором по&nbsp;развитию
     технологий ИИ Сбера» — закрывающий абзац НЕ нужен (замечание
     пользователя 25.09.2026 по лекции Маркова «Съедят ли электроовцы
     людей?…»);
   • лектор упомянут БЕЗ описания или с существенно неполным описанием —
     ОБЯЗАТЕЛЬНО восполнить: либо дополнить описание в том месте, где он
     упоминался (предпочтительно — меньше дублирования), либо добавить
     закрывающий абзац «Лекцию прочитает …» с полным описанием.
Полное описание автора берём там, где оно есть в источнике
      (блок «Лекторы/ведущие», конец текста лекции и т.п.).

 Если лекция является лекцией КУРСА (см. разд. 3а п. 5) и об авторе пишем
 после описания курса — используем «Курс прочитает …», а НЕ «Лекцию
 прочитает …» (решение пользователя 26.09.2026 при прототипе лекции
 Квартальнова TP-4208014; формулировка та же: «Курс прочитает
 <b><i>Фамилия Имя</i></b>, <i>описание</i>»). Для обычных (не курсовых)
 лекций остаётся «Лекцию прочитает …».

## 5а. Дополнительная информация (после аннотации)

Прототип делится на три части: формальные поля (разд. 2), описание
события (шапка + KLBLOCK + аннотация; HTML-код заканчивается на
`</blockquote>`) и «Дополнительная информация» — всё, что идёт сразу же
после `</blockquote>` и до комментария `<!-- @@@ -->`. Сам факультативный
комментарий `<!-- @@@ -->` ставится перед ссылками на источники (на
«Элементах» — именно перед блоком ссылок).

В «Дополнительную информацию» выносим (что есть у события; собираем
из источника, ничего не теряем):

- **Ссылки-приглашения в аннотацию НЕ тащим** (правило пользователя
  01.10.2026, прототип TP-4189525): формулировки вида «узнай больше
  на сайте организатора», «подробности — на Timepad», «все условия на
  сайте» в аннотации (`annot`) и первом абзаце описания ЛИШНИЕ — на
  «Элементах» их не пишут. Все ссылки живут в «Дополнительной
  информации» (блок ссылок после `<!-- @@@ -->`) и в формальных полях
  9/10. Если без такой ссылки теряется смысл — спросить пользователя,
  а не вставлять её молча;

- **Трансляция** — «Будет организована интернет-трансляция лекции…»,
  ссылка на страницу трансляции;
- **Регистрация / покупка билетов** — по образцу «Элементов»:
  `<p>Стоимость билета: <b>1300&nbsp;руб.</b> <a href="..."
  target="_blank">Купить билет</a>.</p>`
  Если ссылок на регистрацию НЕСКОЛЬКО (например, на онлайн-лекцию и на
  очную) — для каждой ссылки делаем ОТДЕЛЬНЫЙ набор кнопок (в одну кнопку
  ссылки не склеиваем). Чем варианты отличаются (очно / онлайн) — поясняем,
  но эти пояснения НЕ включаются в редактируемый/копируемый HTML: они
  остаются в `notes`/комментарии к прототипу (правило пользователя
  01.10.2026, прототипы PM-261001-privody-*).
Стоимость — как в формальном поле «Стоимость» (нижняя граница,
  отдельно трансляция и т.п.); сюда же уместны скидки, условия
  просмотра записи и прочие примечания источника (кроме возрастных
  ограничений — о них отдельное правило ниже);
- **Адрес** (город, улица, дом, зал/аудитория) и **проезд** (метро и т.п.)
  **+ ссылка на карту — ВСЕГДА, когда у события есть офлайн-часть**
  (правило пользователя 26.09.2026: независимо от лектория и от того,
  упомянут ли адрес в источнике — берём формат/адрес/проезд из карточки
  лектория `reference/lectories.md`); **телефон — ФАКУЛЬТАТИВНО**: включаем
  в блок адреса только если организатор его указывает; у только-онлайн
  событий адреса нет;
  Если короткой ссылки на карту НЕТ (только «Карта» из поиска Яндекса —
  `yandex.ru/maps/?text=…` или `/maps/search/…`) — сразу ПОСЛЕ ссылки
  пишем маркер `(ЗАМЕНИТЬ!)`: это напоминание пользователю заменить
  ссылку на точную перед публикацией (правило пользователя 02.10.2026;
  долго жило только в конвейере Medio Modo, ПАМЯТКА разд. 4в). Пример:
  `<a href="https://yandex.ru/maps/?text=…" target="_blank">Карта</a> (ЗАМЕНИТЬ!).`;
  - **ФОРМУЛИРОВКА «ПРОЕЗД» (общее правило пользователя 30.09.2026):
    `<b>Проезд:</b> метро «…»` — БЕЗ «до станции», даже если в образце или
    в источнике написано «до станции метро «…»».** Правило сильнее образца:
    пишем `<b>Проезд:</b> метро «ВДНХ».` (а не «до станции метро «ВДНХ»»),
    при нескольких станциях — перечисление через запятую: `метро «Павелецкая»`,

    метро …` без «до станции». Общее правило: **ПРАВИЛО важнее УСТАРЕВШЕГО

    действительно не покрывает случай;
- **Способы связи** — телефон, почта, Telegram и т.п.;
- **Ссылки на источники и полезные ссылки** — как на «Элементах»:

### Где стоит разделительный комментарий `<!-- @@@ -->` (общее правило для ВСЕХ источников)

Разделитель ставится **одним отдельным элементом массива `extra_html` /
абзацем в HTML — НЕПОСРЕДСТВЕННО перед блоком ссылок, то есть перед
первым абзацем со ссылкой на источник («Информация о лекции на сайте …»,
`class="small"`)**:

```html
<p>Стоимость билетов: <b>от 1200&nbsp;руб.</b> <a …>Купить билет</a>.</p>
<p><b>Контакты организатора:</b> …</p>
<p><b>Адрес:</b> …<br><b>Проезд:</b> … <a …>Карта</a>.</p>
<!-- @@@ -->
<p class="small">Информация о лекции <a …>на сайте …</a>.</p>
```

Зачем так (решение пользователя 29.09.2026): новое описание часто
собирается копированием старого, и комментарий нужен как метка «здесь
меняется ссылка на источник» — чтобы её не забыть и не оставить старую.
Поэтому он не перед блоком «контакты/адрес», а перед самим блоком ссылок.

Проверено на опубликованных страницах: «Архэ» (450626, 450631, 450635) —
разделитель стоит ровно перед блоком ссылок. На странице Medio Modo 450571
он стоит раньше (сразу после цены, перед «Контактами организатора»); нашим
правилом для новых прототипов мы всё равно ставим его перед блоком ссылок.

### Возрастные ограничения (правило пользователя 28.09.2026)

Возрастные ограничения добавляем в «Дополнительную информацию» (и
СОХРАНЯЕМ там) ТОЛЬКО в двух случаях:

1. **18+** — мероприятие только для взрослых;
2. **мероприятие для детей** — в таких случаях может быть важен возраст,
   на которое оно рассчитано (например, «6+»).

Во ВСЕХ остальных случаях возрастные ограничения в «Дополнительную
информацию» НЕ включаем: если возраст есть в источниках — вносим его в
соответствующее поле формальных полей (поле 12 «Возрастные ограничения»,
см. разд. 2); если в источниках его нет — просто оставляем поле пустым.

Что НЕ является основанием для «Дополнительной информации» (уточнение
пользователя 29.09.2026):
- «Куда допускаются в числе прочих и дети» / «дети тоже могут прийти» —
  это про обычное мероприятие, а не про возрастное ограничение. «6+» остаётся
  только в поле 12;
- возраст ДРУГОГО мероприятия того же организатора («у них на сайте где-то
  16+»). Смотрим источник по КОНКРЕТНОМУ событию: у разных мероприятий
  одного организатора возраст бывает разным.

Правило относится к мероприятиям ВСЕХ организаторов. Готовые (уже
одобренные) события при изменении правила не переделываются.

Формат вывода — как у формальных полей и описания, последовательно двумя
видами (не колонками): текстовый вид (читаемо, без тегов) и HTML-код
(абзацы `<p>` со ссылками `<a href="…" target="_blank">…</a>` и &nbsp;,
в fenced-блоке, между абзацами — пустая строка, как в блоке 4).

Текст «Дополнительной информации» проходит те же правила `proofreading`
и `post-check`, что и описание.

## 5б. Обязательная машинная проверка прототипа

Прототип НЕ показывается пользователю, пока не пройдены оба прохода:

1. самопроверка по скиллу `proofreading` п. 0 (отдельный проход по ГОТОВОМУ
   тексту: слив всех nbsp и «ё» с разбором по строкам);
2. финальная пост-проверка по скиллу `post-check` (п. 0 — детерминированный
   валидатор, затем чек-лист).

Пункт 0 пост-проверки — запуск валидатора по САМОМУ файлу прототипа
(не по вручную собранному тексту):

    python -X utf8 tools\check_proto_json.py data\prototypes\<папка>\prototype.json
    python -X utf8 tools\check_proto_json.py          # все прототипы сразу

Валидатор проверяет целиком файл `prototype.json`: формальное поле 1
(«Привязка»), названия, аннотацию, текст лектора, HTML описания и «Дополнительной
информации», имя и описание авторов. Он ловит в т.ч.:
- сырой неразбиваемый пробел U+00A0 (в данных он заменён текстом `&nbsp;`);
- пропущенный лишний nbsp и лишний nbsp там, где нужен обычный пробел;
- неразбиваемые пробелы в буквенных сокращениях («и т. п.») и около римских
  цифр в номерах (Петра&nbsp;I, Екатерины&nbsp;II);
- рассинхрон поля 1 с датой и временем события.

Вывод валидатора прикладывается к результату. «Проверить вручную» не отменяет
запуск скрипта.

## 5в. Организатор прототипа (для фильтра на сайте)

Фильтр «Организаторы» на сайте показывает название места, откуда взята лекция.
Значение определяется по ИСТОЧНИКУ, а не по подзаголовку лекции:

1. если источник — сайт организатора (не Timepad), берётся его домен;
2. если источник — Timepad, берётся аккаунт (поддомен `timepad.ru`);
3. если домен не распознан — берётся город или площадка из прототипа.

Точное название (как в фильтре) задаёт `build.py` (`ORGANIZER_NAMES`):
`spbu.ru` → `Санкт-Петербургский государственный университет`,
`festivalnauki.ru` → `Фестиваль науки NAUKA 0+`, Timepad → поддомен аккаунта.
При появлении нового организатора название добавляется туда же.

Поле 6.3 «Лекторий» при этом может быть прочерком — фильтр работает по
источнику, а не по этому полю.
