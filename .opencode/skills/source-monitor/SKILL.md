# source-monitor — мониторинг источников (сканирование)

Скилл для регулярного (и разового) обзора страниц-списков/афиш из `data/sources_list.md`. Цель — находить новые события **без лишней загрузки** уже обработанных страниц/событий и без преждевременного создания прототипов.

## Главные принципы (обязательны)

1. **Не создавать прототипы сразу.** Сначала формируется реестр кандидатов и очереди (см. ниже).
2. **Экономия времени/загрузок:**
   - Вести **реестр известных событий по каждому источнику** (идентификаторы/канонические ссылки). Если событие с тем же идентификатором (или нормализованной ссылкой источника) уже есть в реестре — **не загружать заново**.
   - После выкачивания **списка (афиши)** источника сравнить полученные ссылки/ID со списком известных для этого источника: выкачивать детально **только новые** (по ID/ссылке). Уже известные пропускать.
   - К событиям из других источников того же лектория, к «Элементам», к прототипам сравнивать **только** события, прошедшие фильтры и признанные кандидатами «новыми» относительно реестра источника (и не отсеянными по правилам ниже).
3. **Ранние отсеивания без выкачки детали** (когда это можно определить по списку): прошедшие даты, нежелательные типы/форматы, нежелательные названия/ключевые слова — по **зафиксированным критериям** (см. раздел «Критерии отбора»). Если критерии не зафиксированы для лектория — помечать как **Сомнительные** и фиксировать вопрос.
4. **Сверка с «Элементами» и сайтом:** предпочтительно сверяться с **локальным сайтом** после обновления (`build.py` / `serve.py`), а не с живым elementy.ru при каждом шаге: сначала `python -X utf8 scrape.py` (при необходимости) и `python -X utf8 build.py`, затем использовать `site/events.json` (или `data/events.json`) как источник правды для уже опубликованных. Прототипы — `data/prototypes/*/prototype.json`. Правила «Элементов» и выкачки — в `data/sources_list.md` (раздел «Элементы…») и `AGENTS.md`.
5. **Отдельно хранить незавершённые решения:** события, отнесённые к **«Нужно»** или **«Сомнительные»**, по которым пользователь ещё не принял финальное решение «добавлять/не добавлять» (или решение отложено), должны лежать в отдельном хранилище **pending** (см. структуру данных).
6. **Запуски:** поддерживать режимы:
   - весь список (все группы/все лектории из реестра запуска),
   - по одной группе лекториев,
   - по отдельным лекториям (по `source_id`/ключу группы в `data/sources_list.md`).

## Где смотреть источники и правила обхода

- Канонический список: **`data/sources_list.md`** (группы по организаторам, URL страниц-списков, способ обхода, примечания). **«Элементы» там не в таблицах мониторинга** — только раздел сверки/выкачки.
- Общие правила проекта: **`AGENTS.md`** (в т.ч. **Timepad — только Edge + CDP**: `tools/cdp_read.py`, `tools/timepad_parse.py`, кэши `data/raw/cdp/`, не начинать с `webfetch` для Timepad), недоступность → `availability_log.md`, повторы 1 мин → 5 мин.
- Процесс обзора и очереди (кратко повторено здесь): **`data/sources_list.md`** раздел «Процесс обзора источников (реестр и очереди)».

## Критерии отбора (важно)

Критерии отбора по лекториям/организаторам должны быть зафиксированы (в примечаниях групп в `data/sources_list.md` или отдельном файле).  
**Сейчас в репозитории они не собраны в одном месте** — если их нет, при разборе кандидатов:
- не выдумывать жёсткие правила;
- всё неоднозначное относить в **Сомнительные** с явной пометкой «нужны критерии/подтверждение пользователя»;
- по возможности предложить пользователю зафиксировать критерии в `data/sources_list.md`.

Типичные ранние фильтры (применять **до** глубокой загрузки деталей, если данные есть в списке): прошедшая дата/время, явный тип «не лекция» (мастер-класс, экскурсия и т.п., если по лекторию запрещено), стоп-слова в названии — только если это правило уже записано.

## Структура данных (рекомендуемая, создавать по мере внедрения)

Все пути относительны корня репозитория.

- `data/monitor/known_by_source.json` — известные события **по источнику** (чтобы не качать повторно).  
  Идея: ключ = `source_id` (стабильный идентификатор группы/ленты из `sources_list.md`, договориться при внедрении), значение = список записей, например `{ "external_id": "...", "url": "...", "first_seen": "YYYY-MM-DD", "last_seen": "YYYY-MM-DD", "title_hint": "..." }`.  
  **Правило:** если `external_id` или нормализованный `url` уже есть — детальную загрузку этого события не делать.

- **Реестр кандидатов** (последний/текущий обзор, объединённый по источникам): хранить в каталоге `data/monitor/` (например файл `registry_candidates.json` или `.jsonl`), поля — дата, название, организатор/лекторий, ссылки, источник, сырой фрагмент. Создаётся при формировании отчёта.

- **`data/monitor/pending.json`** — события со статусом **«Нужно»** или **«Сомнительные»**, по которым **решение пользователя ещё не зафиксировано** (отложено). Отдельно от финальных очередей, чтобы не потерять.

- **Файлы «Не нужно»** — хранить в каталоге `data/monitor/`, с именем по дате (например суффикс даты в имени файла, формат `.json` или `.md`). События, отнесённые к «Не нужно», в диалог **не выводить**, файл сохранять для просмотра; имя и формат фиксируются при первой записи (можно накапливать одним файлом с датами).

- `data/monitor/groups.json` (опционально) — пользовательские **группы лекториев** для запусков («вся группа X раз в неделю»). Если файла нет, группы можно задавать аргументами скрипта/командами скилла и описывать в `sources_list.md`.

Примечание: точные схемы JSON можно уточнять при реализации скриптов; важно соблюдать принципы выше и не терять `pending`/`not_needed`.

## Рекомендуемый порядок прохода (алгоритм)

1. **Подготовка окружения (по ситуации):** при необходимости обновить данные «Элементов» и пересобрать сайт (`scrape.py` → `build.py`), чтобы сверка шла по актуальному `site/events.json`/`data/events.json`. При работе только с прототипами/локальной сверкой — минимум `build.py`, если менялись данные.
2. **Выбрать объём запуска:** все источники / группа из `groups.json` / конкретный `source_id` (из `sources_list.md`).
3. **Для каждого источника:**
   - получить список событий (афишу) **уже существующими способами** (Edge+CDP для Timepad через `tools/cdp_read.py`/`tools/timepad_parse.py` и их кэши; HTML через webfetch/кэши по правилам источника). Не изобретать обход в обход `AGENTS.md`.
   - **Ранние фильтры без глубокой загрузки** (если дата/тип/название видны): отбросить прошедшие, явные нежелательные типы — по зафиксированным критериям; при сомнениях → Сомнительные с пометкой.
   - **Дедуп по реестру источника:** исключить все элементы, чьи `external_id`/нормализованный URL уже есть в `known_by_source.json` для этого `source_id` (их **не загружать** детально).
   - Для оставшихся (новые относительно этого источника) при необходимости загрузить детали **только этих** элементов.
4. **Объединение кандидатов между источниками** одного лектория/тематики (по правилам дедупа проекта: дата+название+автор/ссылки — уточнять по `event-description`/опыту).
5. **Сверка:** с другими источниками этого лектория, с «Элементами» (`site/events.json`/`data/events.json`), с прототипами (`data/prototypes`). Помечать дубли/уже покрытые.
6. **Формирование очередей:** распределить по **Нужно / Сомнительные / Не нужно**.  
   - «Не нужно» — записать в файлы отчёта «Не нужно» в `data/monitor/` (см. структуру данных), **в диалог не выводить** (кроме краткого итога «N записей в файл …»). 
   - «Нужно» и «Сомнительные» — показать пользователю структурировано; то, что требует решения, сохранить/обновить в **`pending.json`** до явного подтверждения/отклонения.
7. **После решения пользователя:** обновить `pending.json`, при добавлении в работу — создавать прототипы/данные уже по обычным скиллам (`event-description`, проверки и т.д.), а в `known_by_source.json` заносить обработанные источниковые ID/URL согласно принятому решению (чтобы в следующий раз не предлагать лишнее повторно) — правила обновления фиксировать в коммитах/заметках.

## Группы и запуск (регулярные прогоны)

- Файл групп: **`data/monitor/groups.json`** (пример уже создан). В нём задаются именованные группы `source_ids`.
- Специальное значение `"__ALL__"` означает: все источники из `data/sources_list.md`, **кроме** раздела «Элементы (сверка и выкачивание)…» (он не является источником мониторинга).
- Режимы запуска (по договорённости при выполнении задачи):
  - **всё:** группа `all` или эквивалент «все источники».
  - **по группе:** указать имя группы из `groups.json` (например `timepad_major`).
  - **по отдельному лекторию/источнику:** указать конкретный `source_id` (соответствует разделу/лента в `data/sources_list.md`; точную схему именования `source_id` зафиксировать при первом внедрении скриптов и при необходимости дописать сюда).
- Регулярные запуски в будущем: планировщик/ручной запуск по группе или по `all`; перед запуском по возможности обновлять сверку с «Элементами» (`scrape.py` → `build.py`) и использовать локальный `site/events.json`/`data/events.json`.

## Скрипты и инструменты (ссылки)

Использовать существующие инструменты репозитория:

- `tools/cdp_read.py`, `tools/timepad_parse.py` — **обязательный путь** для `*.timepad.ru` (Edge + CDP), кэши в `data/raw/cdp/`.
- `tools/elementy_detail.py` и логика из `scrape.py` / `build.py` — для «Элементов» и сборки сайта.
- `scrape.py`, `build.py`, `serve.py` — обновление/сборка локального сайта для сверки.
- При появлении повторяющихся операций создавать вспомогательные скрипты в `tools/` (например нормализация URL, сравнение списков ID, генерация отчётов по очередям) и **ссылаться на них здесь**.

Новые скрипты (планируется добавить по мере нужды): утилиты для чтения/записи `known_by_source.json`, сборки отчёта и очередей, извлечения ID из URL Timepad/ВДНХ и др. После создания скриптов указывать их имена в этом разделе.

## Вывод пользователю (формат результата обзора)

- Краткая сводка: какие источники/группы проверены, сколько в списке до фильтров, сколько отсеяно ранними фильтрами, сколько новых относительно реестра источника, сколько после дедупа с другими источниками/«Элементами»/прототипами.
- **Списки «Нужно» и «Сомнительные»** с полями: источник, название, дата, ссылка на источник, причина попадания в очередь / что непонятно.
- Явно указать: **«Не нужно»: записано в файл `<путь>`** (не дублировать содержимое в чат, если оно объёмное).
- Список **pending** (что ждёт решения) с путём к `data/monitor/pending.json`.

## Безопасность и аккуратность

- Не удалять и не перезаписывать `data/events.json` обходными путями вне принятых скриптов (`scrape.py` и т.д.), если не оговорено отдельно.
- При недоступности источников — `availability_log.md`, повторы по правилам `AGENTS.md`.
- Любые массовые изменения в репозитории коммитить по правилам проекта (проверка скиллов перед коммитом и т.д.).
