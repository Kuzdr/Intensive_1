# source-monitor — мониторинг источников (сканирование)

Скилл для регулярного (и разового) обзора страниц-списков/афиш из `data/sources_list.md`. Цель — находить новые события **без лишней загрузки** уже обработанных страниц/событий и без преждевременного создания прототипов.

## Главные принципы (обязательны)

1. **Не создавать прототипы сразу.** Сначала формируется реестр кандидатов и очереди (см. ниже).
2. **Перед запуском поиска новых событий обновлять наш сайт:** выполнить `python -X utf8 scrape.py` (если нужно по правилам проекта) и `python -X utf8 build.py`, сверку с «Элементами» и уже опубликованными событиями проводить по **локальному** `site/events.json` (и при необходимости `data/events.json`), **не** по живому elementy.ru в ходе каждой проверки, если не оговорено иначе.
3. **Экономия времени/загрузок:**
   - Вести **реестр известных событий по каждому источнику** (`data/monitor/known_by_source.json`). Если событие с тем же идентификатором (или нормализованной ссылкой источника) уже есть в реестре — **не загружать заново**.
   - После выкачивания **списка (афиши)** источника сравнить полученные ссылки/ID со списком известных для этого источника: выкачивать детально **только новые**. Уже известные пропускать.
   - Первичную классификацию **«Нужно / Сомнительные / Не нужно»** делать по информации, доступной в **списке/карточке списка** (название, дата/время, город, короткое описание, тип), **без учёта** наличия в реестре и без учёта совпадений с сайтом/прототипами — это отдельный шаг после. Затем сверять оставшихся кандидатов с реестром (`known_by_source.json`), с локальным сайтом (`site/events.json`/`data/events.json`) и с `data/prototypes/*/prototype.json`.
4. **Ранние отсеивания без глубокой загрузки деталей** (когда ясно по списку): прошедшие даты, явные нежелательные типы (концерт/спектакль/мастер-класс и т.п., если по критериям не подходят), явные стоп-критерии — по зафиксированным критериям лектория. Если критериев нет — **Сомнительные** с пометкой.
5. **Пагинация списков (особенно Timepad):** если есть пагинация (`?page=N`, `/events/all/page/N/` и т.п.), проходить страницы по порядку. **Определение «докуда идти» (Timepad):** в карточках списка есть относительные пометки: будущее — «через …» (дни/часы), «сегодня», «завтра»; прошедшее — «… назад», «вчера», «позавчера». Собираем события **только с будущими** пометками. Если на очередной странице **все** карточки прошедшие — останавливаемся. Если на странице есть и будущие, и прошедшие — берём только будущие (обычно будущие идут выше), а на следующую страницу уже не идём (дальше, как правило, прошедшие). Если на первой проверяемой странице уже только прошедшие — дальше не идём. **Не «листать до повтора/пустоты»:** 26.11.2026 это привело к ненужным `page=3..8` у ВДНХ — прошедшие у `lektorij-vdnh` начались уже на `page=2`.
6. **Повторные попытки при сбоях скачивания:** при ошибках сети/таймаутах/обрывах (в т.ч. CDP) делать **разумное число повторных попыток** (например 2–3), с короткой паузой; не бросать источник после первой неудачи без попыток. При недоступности — фиксировать в `availability_log.md` по правилам `AGENTS.md`.
7. **Отдельно хранить незавершённые решения** в `data/monitor/pending.json` (Нужно/Сомнительные без финала).
8. **Запуски:** весь список / группа из `groups.json` / отдельный источник (`source_id`).

## Где смотреть источники и правила обхода

- Канонический список: **`data/sources_list.md`** (группы по организаторам, URL страниц-списков, способ обхода, примечания). **«Элементы» там не в таблицах мониторинга** — только раздел сверки/выкачки.
- Общие правила проекта: **`AGENTS.md`** (в т.ч. **Timepad — только Edge + CDP**: `tools/cdp_read.py`, `tools/timepad_parse.py`, кэши `data/raw/cdp/`, не начинать с `webfetch` для Timepad), недоступность → `availability_log.md`, повторы 1 мин → 5 мин.
- Процесс обзора и очереди (кратко повторено здесь): **`data/sources_list.md`** раздел «Процесс обзора источников (реестр и очереди)».

## Критерии отбора (важно)

Критерии отбора по лекториям/организаторам должны быть зафиксированы (в примечаниях групп в `data/sources_list.md` или отдельном файле).  
**Сейчас в репозитории они не собраны в одном месте** — если их нет, при разборе кандидатов:
- не выдумывать жёсткие правила;
- всё неоднозначное относить в **Сомнительные** с явной пометкой «нужны критерии/подтверждение пользователя»;
- по возможности предложить пользователю зафиксировать критерии в `data/sources_list.md`.

Типичные ранние фильтры (применять **до** глубокой загрузки деталей, если данные есть в списке): прошедшая дата/время, явный тип «не лекция» (мастер-класс, экскурсия и т.п., если по лекторию запрещено), стоп-слова в названии — только если это правило уже записано.

## Структура данных (рекомендуемая, создавать по мере внедрения)

Все пути относительны корня репозитория.

- `data/monitor/known_by_source.json` — известные события **по источнику** (чтобы не качать повторно).  
  Идея: ключ = `source_id` (стабильный идентификатор группы/ленты из `sources_list.md`, договориться при внедрении), значение = список записей, например `{ "external_id": "...", "url": "...", "first_seen": "YYYY-MM-DD", "last_seen": "YYYY-MM-DD", "title_hint": "..." }`.  
  **Правило:** если `external_id` или нормализованный `url` уже есть — детальную загрузку этого события не делать.

- **Реестр кандидатов** (последний/текущий обзор, объединённый по источникам): хранить в каталоге `data/monitor/` (например файл `registry_candidates.json` или `.jsonl`), поля — дата, название, организатор/лекторий, ссылки, источник, сырой фрагмент. Создаётся при формировании отчёта.

- **`data/monitor/pending.json`** — события со статусом **«Нужно»** или **«Сомнительные»**, по которым **решение пользователя ещё не зафиксировано** (отложено). Отдельно от финальных очередей, чтобы не потерять.

  **Статусы после решения пользователя (26.11.2026, обход ВДНХ):** «Не решено» → `undecided`
  (вернуться позже, событие остаётся в `pending.json`), «Нужно, но требует обновления
  источника» → `needs_update` (прототип создан, но часть данных временная — например,
  регистрация ещё не открыта; вернуться к нему после указанной даты). Оба статуса
  допустимы в `data/sweep/known_events.json` (`tools/sweep_lectories.py`, `STATUSES`)
  и в статусах `data/monitor/known_by_source.json`. Прототип со статусом `needs_update`
  НЕ считается законченным: в `notes` прототипа указывается, что и когда перепроверить.

- **Файлы «Не нужно»** — хранить в каталоге `data/monitor/`, с именем по дате (например суффикс даты в имени файла, формат `.json` или `.md`). События, отнесённые к «Не нужно», в диалог **не выводить**, файл сохранять для просмотра; имя и формат фиксируются при первой записи (можно накапливать одним файлом с датами).

- `data/monitor/groups.json` (опционально) — пользовательские **группы лекториев** для запусков («вся группа X раз в неделю»). Если файла нет, группы можно задавать аргументами скрипта/командами скилла и описывать в `sources_list.md`.

Примечание: точные схемы JSON можно уточнять при реализации скриптов; важно соблюдать принципы выше и не терять `pending`/`not_needed`.

## Рекомендуемый порядок прохода (алгоритм)

1. **Подготовка окружения:** перед запуском поиска новых событий **обновить наш сайт**: `python -X utf8 scrape.py` (при необходимости, по правилам проекта) → `python -X utf8 build.py`. Сверку с уже опубликованными событиями делать по **локальному** `site/events.json` (и при необходимости `data/events.json`), **не** по живому elementy.ru в ходе каждой проверки.
2. **Выбрать объём запуска:** все источники / группа из `groups.json` / конкретный `source_id` (из `sources_list.md`).
3. **Для каждого источника:**
   - получить список событий (афишу) существующими способами (Edge+CDP для Timepad через `tools/cdp_read.py`/`tools/timepad_parse.py` и кэши; HTML/webfetch/кэши по правилам источника). При сбоях — **повторные попытки** (разумное число, напр. 2–3) с паузой, не останавливаться после первой ошибки.
   - **Пагинация:** если есть страницы/«дальше», пройти **все** страницы и собрать полный список.
   - **Первичная классификация по списку** (без учёта реестра и без сверки с сайтом/прототипами): по названию, дате/времени (если есть), городу, типу, короткому описанию распределить в **«Нужно / Сомнительные / Не нужно»**. Явные не подходящие типы (концерт/спектакль/детская программа и т.п. — по критериям) → «Не нужно» с пометкой; неоднозначное → «Сомнительные».
   - **Дедуп по реестру источника:** исключить элементы, уже есть в `known_by_source.json` для этого `source_id` (их не предлагать повторно; при необходимости отметить).
   - Для оставшихся после первичной классификации и исключения известных: при недостатке данных — загрузить детали (с повторными попытками). Затем **сверка** с локальным сайтом (`site/events.json`/`data/events.json`) и с `data/prototypes/*/prototype.json` (по дате/названию/автору/ссылкам) и при необходимости с другими источниками того же лектория.
4. **Формирование итоговых очередей:** уточнить «Нужно/Сомнительные/Не нужно» с учётом сверки; «Не нужно» — в файл в `data/monitor/` (не в чат, кроме краткого итога); «Нужно/Сомнительные» — пользователю и/или в `pending.json`.
5. **После решения пользователя:** обновить `pending.json`, при добавлении — прототипы по обычным скиллам, в `known_by_source.json` заносить обработанные ID/URL.

## Группы и запуск (регулярные прогоны)

- Файл групп: **`data/monitor/groups.json`** (пример уже создан). В нём задаются именованные группы `source_ids`.
- Специальное значение `"__ALL__"` означает: все источники из `data/sources_list.md`, **кроме** раздела «Элементы (сверка и выкачивание)…» (он не является источником мониторинга).
- Режимы запуска (по договорённости при выполнении задачи):
  - **всё:** группа `all` или эквивалент «все источники».
  - **по группе:** указать имя группы из `groups.json` (например `timepad_major`).
  - **по отдельному лекторию/источнику:** указать конкретный `source_id` (соответствует разделу/лента в `data/sources_list.md`; точную схему именования `source_id` зафиксировать при первом внедрении скриптов и при необходимости дописать сюда).
- Регулярные запуски в будущем: планировщик/ручной запуск по группе или по `all`; перед запуском по возможности обновлять сверку с «Элементами» (`scrape.py` → `build.py`) и использовать локальный `site/events.json`/`data/events.json`.

## Скрипты и инструменты (ссылки)

Использовать существующие инструменты репозитория:

- `tools/cdp_read.py`, `tools/timepad_parse.py` — **обязательный путь** для `*.timepad.ru` (Edge + CDP), кэши в `data/raw/cdp/`.
- `tools/cdp_vdnh_collect.py` — обход `vdnh.ru` через Edge/CDP: фильтр «Все фильтры» → «Лекции» → «Применить», подгрузка «Показать еще», снимки DOM и карточек.
- `tools/cdp_vdnh_timepad_collect.py` — обход пяти Timepad-лент ВДНХ через Edge/CDP **с остановкой на первом прошедшем событии** (26.11.2026 будущие закончились уже на `page=2`; страницы `page=3..` не открываем).
- `tools/vdnh_monitor_report.py` — сводка по сохранённым снимкам без сети: дедупликация, сверка с `data/events.json` и прототипами, запись отчёта (например, `run_vdnh_2026-11-26.md`), списка «не нужно» и файлов `known_by_source.json`, `pending.json` в каталоге `data/monitor/`.
- `tools/elementy_detail.py` и логика из `scrape.py` / `build.py` — для «Элементов» и сборки сайта.
- `scrape.py`, `build.py`, `serve.py` — обновление/сборка локального сайта для сверки.
- При появлении повторяющихся операций создавать вспомогательные скрипты в `tools/` (например нормализация URL, сравнение списков ID, генерация отчётов по очередям) и **ссылаться на них здесь**.

Новые скрипты (планируется добавить по мере нужды): утилиты для чтения/записи `known_by_source.json`, сборки отчёта и очередей, извлечения ID из URL Timepad/ВДНХ и др. После создания скриптов указывать их имена в этом разделе.

## Вывод пользователю (формат результата обзора)

- Краткая сводка: источники/группы, объём списка, пройдены ли все страницы (пагинация), сколько отсеяно по первичной классификации (по списку), сколько исключено по `known_by_source.json`, итоги сверки с локальным сайтом (`site/events.json`/`data/events.json`) и прототипами.
- **Таблицы кандидатов** (где уместно) включать поля: **название, дата, время** (если есть в источнике), город/площадка (кратко), ссылка, источник, первичная оценка, комментарий.
- Списки **«Нужно» и «Сомнительные»** — структурировано; **«Не нужно»** — записать в файл в `data/monitor/` и указать путь (в чат не дублировать объёмно).
- Список **pending** с путём к `data/monitor/pending.json`.

## Безопасность и аккуратность

- Не удалять и не перезаписывать `data/events.json` обходными путями вне принятых скриптов (`scrape.py` и т.д.), если не оговорено отдельно.
- При недоступности источников — `availability_log.md`, повторы по правилам `AGENTS.md`.
- Любые массовые изменения в репозитории коммитить по правилам проекта (проверка скиллов перед коммитом и т.д.).
